QwenLM/Qwen3-Embedding
category: embeddings-models   |   steal priority: MUST

siblings: ./00-index.txt   |   map: ../../README.txt

what:        A family of decoder-only LLM-based text embedding/reranker models (0.6B/4B/8B, dims
             1024/2560/4096) using causal last-token (EOS) pooling, instruction-prefix
             conditioning, and Matryoshka Representation Learning so a single vector can be
             truncated to as few as 32 dims and re-normalized with minimal retrieval loss.
innovation:  Matryoshka Representation Learning makes embedding dimensionality a near-lossless, deterministic
             compression knob via nested-prefix-trained vectors that stay valid under
             truncate-then-renormalize.
techniques:
  - Matryoshka Representation Learning: nested-prefix loss front-loads importance so vec[:d] for
    d in {32,64,128,256,512,768,1024} is independently usable
  - Truncate-then-renormalize: slice the first d dims then L2-normalize so dot product == cosine
    remains exact on the prefix
  - Last-token (EOS) causal pooling: final hidden state aggregates the whole sequence under the
    causal mask (no [CLS]), with left/right padding handling
  - Instruction-prefix conditioning: 'Instruct: {task}\nQuery: {q}' template steers the same
    weights per task, +1-5% with no retraining
  - L2-normalized output vectors as the contract so similarity is a plain dot product
  - Per-model fixed full dim (1024/2560/4096) advertised as the MRL ceiling
nest steals: nest-format: add an MRL-aware dimension-truncation codec/manifest field on the embeddings
             section. The Python builder (nest-python) records the model's full dim plus a
             chosen mrl_dim (e.g. 256 of 1024); it truncates each vector to the prefix and
             re-L2-normalizes before writing, storing mrl_dim and full_dim in the embeddings
             section header / search_contract. nest-runtime's SIMD dot-product kernels already
             score raw f32/f16/int8 straight from mmap, so they need only honor the smaller
             per-vector stride from the manifest; the exact-cosine rerank still returns true
             cosine because vectors are renormalized on the truncated prefix. This stacks
             multiplicatively with the existing tiny preset (int8): a 256-of-1024 MRL prefix at
             int8 is 4x (dims) * 4x (int8 vs f32) = ~16x smaller embeddings than f32-1024, while
             exact rerank guarantees the returned score is real cosine on the stored prefix. Add
             a CLI flag (nest-cli build/stats) to surface mrl_dim and the size/recall tradeoff.
             Determinism is preserved: truncation is a pure deterministic slice, so same chunks
             + same model fingerprint + same mrl_dim => byte-identical file. Stays additive (new
             manifest field + reserved encoding id), single-file, offline.
compression: Directly central to the 'compress more than everyone' north star. MRL adds a compression axis
             nest does not yet exploit: the embedding-dimension axis, independent of and
             multiplicative with the value-precision axis (int8/f16) nest already has. Qwen
             reports truncating 4096->1024 keeps ~95% retrieval while cutting storage 75%; for
             nest's tiny preset, a 256-of-1024 int8 layout could roughly quarter the dominant
             on-disk cost (embeddings are usually the largest section) at small recall cost, and
             because the format mandates exact-cosine rerank, the headline score stays honest.
             It also shrinks the HNSW index footprint since graph vectors are shorter.
perf:        Truncation is a contiguous prefix slice, so per-vector memory stride shrinks linearly with
             mrl_dim and the existing AVX2/NEON dot-product kernels run unchanged on the shorter
             stride (fewer SIMD lanes per vector => proportionally faster scoring and smaller
             mmap working set). No new entropy coder or transform needed; cost is one L2 renorm
             per vector at build time only. Shorter vectors also reduce HNSW distance-eval cost
             and index size. The models themselves are heavy (0.6B params, BF16, 32K ctx, RoPE),
             but nest only consumes their float outputs, so the model weight is irrelevant to
             the runtime; only the build-time embedder cares.
