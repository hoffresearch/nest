what:        A PostgreSQL extension implementing exact + approximate (HNSW, IVFFlat) vector search over four
             vector types (float32 vector, float16 halfvec, binary bit, sparsevec) with
             scalar/binary quantization codecs, distance operators for
             L2/cosine/inner-product/L1/Hamming/Jaccard, and a
             binary-quantize-coarse-filter-then-exact-rerank retrieval pattern.
innovation:  The binary-quantize-then-exact-rerank pipeline.
techniques:
  - binary_quantize(): sign-bit threshold at zero (x>0 -> 1, x<=0 -> 0), packing each dim into 1
    bit -> dimensions/8 + 8 bytes, scored via Hamming distance (popcount of XOR)
  - halfvec scalar quantization: IEEE float16 (2 bytes/dim) giving 2.0-3.0x shrink with
    near-identical recall because the most significant bits dominate distance
  - sparsevec compressed encoding: store only non-zeros as (index,value) pairs, 8 bytes per nnz
    + 16 byte header, format {1:0.1,3:0.2}/dim
  - HNSW on-disk layout: 36-byte HnswMetaPageData (magic 0xA953A953, m, efConstruction, entry
    blkno/offno/level, insertPage) on page 0; element tuples carry vector inline + heaptids[10]
    dedup array + 6-byte neighbortid pointer; neighbor tuples sized (level+2)*m with 6-byte
    ItemPointerData refs
  - two-stage retrieval: over-fetch K' (e.g. 800) by quantized distance, then ORDER BY exact
    distance LIMIT K (e.g. 10)
  - heaptids[10] dedup: identical vectors share one graph node, collapsing duplicate embeddings
  - expression/cast indexing: index embedding::halfvec or binary_quantize(embedding)::bit so the
    same source column drives multiple quantized indexes
  - iterative index scans (strict_order/relaxed_order) to keep filtering past the first
    ef_search batch without recall collapse
nest steals: Add a binary quantization tier to nest-format encoding (next reserved encoding id, additive
             within v1): a binary codec that sign-bit-thresholds each embedding dim at 0 into a
             packed bitmap section, dimensions/8 bytes per vector vs 4 bytes/dim raw = ~32x
             shrink on the embeddings section, which is nest's single largest section and the
             one its zstd policy refuses to touch. In nest-runtime, add a Hamming popcount
             kernel to the simd dispatcher (AVX2 _mm256 popcnt / NEON vcnt / scalar count_ones)
             that scores the bit vectors straight off mmap, used ONLY as a coarse candidate
             generator that over-fetches K*~50-80x, then feeds nest's already-mandatory exact
             cosine rerank, materializing real f32 from a sidecar full-precision embeddings
             section (or from int8). This yields a new "nano" preset below tiny that beats 0.283
             size ratio while the search_contract guarantee (returned score is always real
             cosine) is preserved unchanged. Separately, adopt the heaptids-style dedup in
             nest-format writer: chunks whose embeddings are byte-identical collapse to one
             stored vector, helping the deterministic-build/compress-more goal. The sparsevec
             (index,value) encoding maps directly onto nest's bm25_index(0x08) and any future
             sparse-embedding section. Skip pgvector's page/TOAST machinery entirely
             (Postgres-coupled, irrelevant to a single mmapped file).
compression: Directly central. Binary quantization is the highest-leverage missing codec for nest's "compress
             more than everyone" north star: the embeddings section is the dominant volume and
             is deliberately excluded from zstd, so a 1-bit-per-dim packed bitmap (~32x over raw
             f32, ~8x over int8) is the biggest single win available, and pgvector proves with
             real recall numbers (91-99% at 1536-dim with rerank) that the exact-rerank step
             nest already mandates is exactly what makes it safe. halfvec confirms nest's
             float16 choice; sparsevec gives a concrete encoding for sparse sections.
perf:        halfvec doubles vectors-per-page and gives identical-or-better QPS/latency vs float32. Binary
             quantization stacked with halfvec gave 67x HNSW build speedup (0.7.0 vs 0.5.1).
             Hamming distance is a single XOR + popcount per vector, far cheaper than f32 dot
             product, so the coarse stage is near-free; recall depends on bit-diversity (fails
             on low-dim sift-128/gist-960, excels at high-dim 1536). Over-fetch ratio (e.g.
             800-to-10 = 80x) is the recall/cost knob. HNSW graph must fit in RAM in pgvector;
             nest sidesteps this by mmapping the whole file and letting the OS page it.
