what:        Apache Jena is a Java RDF/SPARQL framework whose TDB2 store persists triples as three permuted
             B+tree indexes (SPO/POS/OSP, six for quads) over 8-byte NodeIds resolved through a
             dictionary node table, with scalar values inlined directly into the NodeId to skip
             the dictionary entirely.
innovation:  NodeId tagged-union inlining: an 8-byte (64-bit) identifier uses bit 63 as a discriminator - 0
             means the low 63 bits are a pointer (file offset) into the dictionary node table; 1
             means the value is self-contained in the id. A second tag bit then selects an
             encoding: doubles (62-bit double with exponent range reduced 2 bits), or a 6-bit
             XSD-type field + 56-bit value carrying signed integers, decimals (8-bit scale +
             48-bit signed mantissa), dates/datetimes at ms precision, and booleans. The win:
             common scalar literals carry their full value in the index key itself, so they
             never allocate a dictionary entry, never trigger a hash lookup, and sort/compare
             correctly inline. The dictionary is only paid for strings/URIs/IRIs that genuinely
             need it.
techniques:
  - NodeId tagged-union: bit63 ptr-vs-value, bit62 sub-encoding select, 6-bit xsd type + 56-bit
    payload
  - Inline scalar encodings: 56-bit signed int, 8-bit-scale+48-bit decimal, ms-precision
    date/datetime, boolean, range-reduced 62-bit double
  - Dictionary node table: bidirectional Node<->NodeId via 128-bit MD5 hash key plus sequential
    value file for reverse lookup
  - Permuted multi-index storage: 3 B+trees SPO/POS/OSP (6 for quads) each holding full tuple,
    enabling index-only scans for any bound prefix
  - Fixed-length-key/fixed-length-value custom B+tree (keys are packed NodeId tuples, no
    variable-length records)
  - Rule-based cardinality estimation (stats.opt) reordering patterns by selectivity tokens
    VAR/TERM/URI/LITERAL
  - xloader bulk build: emit binary tuples, external merge-sort via unix sort(1), compress
    intermediate sort runs to shrink peak temp space, build each index as a separate streamed
    phase
  - Copy-on-write MVCC B+tree blocks for single-writer/multi-reader without blocking readers
nest steals: Two concrete steals. (1) Tagged-NodeId inlining maps onto nest-format as a typed-scalar codec
             for structured payloads (json/yaml/parquet columns, dataset cells): instead of a
             flat chunks_canonical text section, add a future column/value section where each
             cell is an 8-byte tagged word - bit63 = inline-vs-span, lower bits = a 4-bit
             encoding tag + payload (i56 int, 8-bit-scale i48 decimal, ms-epoch date, bool,
             f16/range-reduced double). Numbers/dates/bools cost zero dictionary bytes and zero
             chunk-span indirection; only strings keep a chunks_original_spans pointer. This is
             a new RESERVED section id (0x09+) and a new encoding id (4-255) - fully additive
             within v1, no NEST_FORMAT_VERSION bump. Directly advances
             compress-more-than-everyone for tabular/json corpora where today every integer
             round-trips through text+zstd. (2) The xloader pattern - stream tuples,
             external-merge-sort, compress intermediate runs - is the blueprint for
             nest-python's deterministic builder when corpora exceed RAM: sort chunk_ids/terms
             with a stable alphabetical external sort (matching the bm25
             deterministic-term-order constraint), zstd the spill files, build
             hnsw_index(0x07)/bm25_index(0x08) as separate streamed passes; keeps builds
             deterministic/reproducible while removing the in-RAM ceiling. (3) Reference-only:
             SPO/POS/OSP permuted-index idea informs a future graph-search section - store an
             edge tuple in multiple sort orders so any bound prefix is an index-only range scan,
             the on-disk substrate for the north-star graph search.
compression: High for structured/tabular data. The inline-NodeId trick is a domain-specific entropy win
             orthogonal to zstd: it removes dictionary entries and span-pointer indirection for
             the most common literal types (ints, dates, bools, decimals), packing each into <=8
             self-describing bytes that also sort correctly. For json/yaml/parquet/dataset
             payloads (explicitly in nest north-star scope) this beats text+zstd because zstd
             still pays for the textual representation and a per-value span offset. The
             embedding hot path and mandatory exact-cosine rerank are untouched - this is a
             non-embedding section, so it can even be zstd-wrapped on top.
perf:        NodeIds are fixed 8 bytes, so B+tree keys are fixed-length tuples - comparisons are word-aligned
             integer compares, ideal for branchless/SIMD-friendly scanning and mmap-resident
             range scans (matches nest mmap + scalar/AVX2/NEON dispatch). Inline values avoid a
             random dictionary read (MD5-keyed hash lookup) per scalar, a large latency saving
             on selective queries. xloader compresses intermediate sort runs to cut peak temp
             disk substantially. MVCC copy-on-write blocks give lock-free readers; for nest
             (read-mostly, mmap, offline) the takeaway is fixed-width keys + permuted sort
             orders, not the transaction machinery.
