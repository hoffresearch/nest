what:        A Git-for-data document/graph database whose Rust storage core (terminus-store) stores RDF
             triples as immutable, content-addressed delta layers built from HDT-derived
             succinct data structures (front-coded string dictionaries, bit-packed integer
             arrays, and rank/select bit vectors over adjacency lists), reaching ~13 bytes per
             triple.
innovation:  Decompose data into integer-ID triples and store the whole thing as a stack of immutable,
             content-addressed "delta layers", where each layer is built entirely from
             query-time-no-decompression succinct structures: a Plain-Front-Coded (PFC) string
             dictionary that assigns implicit integer IDs by sorted position, bit-packed
             fixed-width LogArrays for the ID columns, and a two-level block/superblock
             rank-select bit index over adjacency-list bit sequences. Compression and the
             queryable index are the SAME bytes, so you search directly on the compressed form,
             and new data is just another append-only layer addressed by the hash of its
             content.
techniques:
  - Plain Front Coding (PFC) string dictionary: lexicographically sort strings, fixed-size
    buckets, store shared-prefix-length + suffix per entry; ID = implicit sorted position;
    bidirectional id<->string via bucket binary search (Martinez-Prieto INFOSYS 2016)
  - LogArray: bit-packed array of fixed-width integers using ceil(log2(max+1)) bits per slot
    instead of fixed u32/u64, with explicit on-disk width header for portability
  - Two-level rank/select BitIndex: 64-bit blocks grouped into superblocks (SBLOCK_SIZE=52),
    precomputed block+superblock popcount tables stored as LogArrays; rank = sblock_rank +
    block_rank + masked popcount; select via binary search over superblocks then a 64-bit scan
  - Adjacency-list triple encoding: SP and SPO orderings expressed as bit sequences + LogArrays
    (HDT bitmap-triples model) so subject->predicate->object navigation is rank/select with no
    pointers
  - Content-addressed immutable delta layers: every commit is a new layer named by a 20-byte
    hash; additions+removals stored separately; queries resolve current state by traversing the
    layer stack newest-wins
  - Delta rollup compaction: periodically squash the layer stack into a fresh base layer to
    bound read amplification and in-memory footprint
  - Single-archive on-disk format (v0.20+): all primitive structure files for a layer bundled
    into one mmap-friendly archive blob, ~13 bytes/triple on billion-triple sets
  - Buffer-oriented zero-copy structures: every structure is parsed as a view over an existing
    (mmappable) byte buffer rather than heap-constructed, so reads operate straight off disk
nest steals: Two concrete steals into nest-format. (1) Add a PFC codec (encoding id in the reserved 4-255
             range) for the non-embedding string sections, primarily chunk_ids and provenance,
             and for nest's future json/yaml/dataset payloads: front-coding crushes
             URI/path/repeated-prefix data far below generic zstd while staying queryable.
             Implement as crates/nest-format/src/encoding/pfc.rs plus a bucketed FrontCodedDict
             reader in nest-runtime so id<->string lookups run zero-copy off mmap. (2) Add a
             LogArray + two-level rank/select BitIndex primitive
             (crates/nest-runtime/src/succinct/ logarray.rs + bitindex.rs, each <300 lines) and
             use it to shrink the HNSW index section (0x07): replace u32 neighbor-id arrays with
             ceil(log2(N))-bit LogArrays and represent level/neighbor occupancy bitsets with
             rank/select. This directly attacks the 'tiny' preset size ratio (0.283) by removing
             wasted high bits in every adjacency list while keeping deterministic, seekable
             layout. The content-addressed delta-layer idea maps onto nest's existing
             content_hash + nest://content_hash/chunk_id citation model: it is the blueprint for
             nest's real-time-edit goal, append an immutable additive layer-section (reserved id
             0x09+) carrying added/removed chunk_ids + embeddings, resolved newest-wins at query
             time, with periodic rollup to a fresh base file, all without breaking the FROZEN v1
             single-file determinism.
compression: Directly central to nest's north star of compress-more-than-everyone. PFC is a domain-specific
             entropy win on exactly the structured/prefix-heavy data nest wants to ingest
             (paths, URIs, JSON keys, dataset columns) that generic zstd misses, and it stays
             query-without-decompress. LogArray + rank/select removes the largest source of
             slack in nest's ANN index (fixed-width 32-bit IDs over small N), shrinking the
             index section that dominates the 'tiny' preset footprint. The ~13 bytes/triple
             result is the proof that succinct-but-queryable beats compress-then-decompress for
             the search hot path, the same principle nest already applies by never
             zstd-compressing embeddings.
perf:        Succinct structures are queried with no decompression: rank/select are O(1) (block+superblock
             table lookup plus one 64-bit popcount); select is O(log superblocks) binary search
             then a single-word scan. All structures are buffer-views (Bytes) over a single
             mmappable archive, so reads happen straight off disk with zero heap copy,
             architecturally identical to nest's mmap+SIMD hot path. Reported ~13 bytes/triple
             in-memory on billion-triple datasets. Two-level index overhead is small (blocks
             every 64 bits, superblocks every 52 blocks, a few percent). Cost: read
             amplification grows with layer-stack depth, mitigated by periodic delta rollup, a
             tradeoff nest must budget if it adopts append-only edit layers.
