RDFLib/rdflib
category: semantic-rdf   |   steal priority: MEDIUM

siblings: ./00-index.txt   |   map: ../../README.txt

what:        A pure-Python RDF toolkit whose in-memory Store indexes triples in three redundant permutation
             dictionaries (SPO/POS/OSP) plus context maps, and evaluates SPARQL 1.1 via an
             algebra of lazy nested-loop joins with dynamic most-bound-first triple-pattern
             reordering.
innovation:  The "triple of permutations" index: store every edge three times under SPO, POS, and OSP
             nested-dict orderings so that any of the eight subject/predicate/object binding
             patterns resolves to a direct prefix walk (O(1) descent then iterate), giving
             symmetric fast lookup no matter which graph terms are known. This is the canonical
             compact way to make a graph adjacency structure queryable from any direction
             without a query planner.
techniques:
  - Three permuted nested-dict indices SPO/POS/OSP, each leaf=presence bit, so any bound-prefix
    (s, sp, p, po, o, os, spo, none) maps to one permutation's descent
  - Term-as-interned-string: all terms subclass Python str (URIRef/BNode/Literal) so identity
    reuses CPython string interning; Literal hash = str_hash XOR hash(lang.lower()) XOR
    hash(datatype) to fold the 3-tuple into one dict key
  - Context/quad layering: triple->{context:quoted_bool} map plus inverse context->set(triple)
    map sit on top of the shared triple indices so named graphs share one physical edge (dedup
    across graphs)
  - SPARQL BGP evaluation as recursive algebra with dynamic triple-pattern reordering by count
    of already-bound variables (most-selective-first heuristic), no cost statistics needed
  - Lazy nested-loop join (evalLazyJoin) with push-down of bound variables into the next pattern
    and FrozenBindings immutable solution mappings instead of materializing intermediate
    relations
  - Pluggable Store API (add/remove/triples(pattern)/contexts) decoupling the graph algebra from
    physical storage (memory, BerkeleyDB, remote SPARQL)
nest steals: Adopt the three-permutation triple index as a new OPTIONAL nest-format section (next reserved id
             0x09) to deliver the north-star "graph search" capability over chunk relationships.
             Concretely: in nest-format add a graph_index section storing edges as three sorted
             little-endian u32 arrays (SPO, POS, OSP) over integer-densified term ids, plus a
             term dictionary section mapping term-id->canonical string (reuse the existing
             chunk_ids interning pattern). Because each permutation is monotonically sorted,
             store it delta+varint or just sort and let zstd(non-embedding section) crush it --
             graph edges are highly compressible, which directly serves "compress more than
             everyone." In nest-runtime add a graph::TripleIndex that mmaps the three arrays and
             does binary-search prefix walks (no dict, no allocation) to answer any
             bound-pattern, then port RDFLib's most-bound-first BGP reordering as a
             deterministic seeded join order (alphabetical/id-order tiebreak) so multi-hop graph
             queries stay reproducible and never panic (typed thiserror). nest-cli gains a
             search-graph subcommand; nest-python exposes pattern queries. The XOR-folded term
             hashing and str-interning idea informs how to dedup term strings in the dictionary
             section. Files stay <=300 loc by splitting graph/term_dict.rs, graph/index.rs,
             graph/join.rs.
compression: High for the graph modality: the three-permutation layout looks 3x redundant but each
             permutation is a sorted integer sequence, so delta-coding + zstd makes the
             redundancy near-free while unlocking direction-agnostic queries; term-id
             densification + a string dictionary turns long repeated URIs/strings into small
             ints (dictionary compression), and cross-graph edge sharing (one physical edge,
             many contexts) is exactly the dedup nest wants when compressing whole
             databases/repos into one .nest container.
perf:        Pure Python, dict-of-dict-of-dict: fast for interactive use but memory-heavy (every edge stored
             3x as Python objects, ~hundreds of bytes/triple) and not mmap-able; scales to ~low
             millions of triples in RAM, not billions. The lazy nested-loop join has no
             hash-join, so large joins are O(n*m) in the worst case. nest should keep the
             algorithmic shape (3 permutations, most-bound-first reorder) but replace Python
             dicts with sorted mmap'd u32 arrays + binary search to get zero-allocation,
             SIMD-free but cache-friendly prefix scans straight off disk.
