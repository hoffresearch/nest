what:        A byte-aligned LZ77 compressor with no entropy coder, whose block format is a stream of [token |
             literal-length-extension | literals | 2-byte LE offset | match-length-extension]
             sequences decodable at multiple GB/s per core via branch-light wildcopy.
innovation:  A deliberately entropy-coder-free, byte-aligned block format whose decoder is so simple (no
             bit-unpacking, no Huffman/FSE tables, just memcpy-style literal and match copies)
             that decompression runs at RAM-bandwidth speed -- trading a few points of ratio for
             the ability to decode in a latency-critical hot path.
techniques:
  - token byte split into two nibbles: high 4 bits = literal length, low 4 bits = match length
    (both 0-15)
  - LSIC (Linear Small-Integer Code) varint extension: when a nibble is 15, read add-255
    continuation bytes until a non-255 byte, summing them onto the length
  - minmatch=4: match-length nibble of 0 already means a 4-byte copy, so the encoded value is
    matchlen-4, saving the unrepresentable short matches
  - 2-byte little-endian back-reference offset, max 65535 (64KB sliding window); offset 0 is
    reserved as a corruption sentinel
  - hash table over 4-byte sequences mapping prefix->latest position for O(1) greedy match
    finding; LZ4_HC adds chain tables / lazy+optimal parsing for higher ratio at lower speed
  - wildcopy: copy literals and matches in fixed 8-byte machine-word chunks past the exact
    length (requires output over-allocation slack) to eliminate per-byte branching
  - frozen end-of-block invariants (last 5 bytes always literals, last match >=12 bytes before
    end) that let speed-oriented decoders skip bounds checks
  - frame layer (magic 0x184D2204, FLG/BD descriptor) with selectable 64KB/256KB/1MB/4MB block
    sizes, optional block-linking within the 64KB window, and xxHash-32 block/content checksums
nest steals: Add an lz4 block codec to nest-format/src/encoding/ as a new wire-encoding id (reserve one of
             the free 4-255 slots, additive within v1, registered in layout alongside
             SECTION_ENCODING_ZSTD and wired into decode_payload in encoding/mod.rs). Its
             purpose is NOT to beat zstd on cold sections (zstd already wins on ratio) but to be
             the first compressor nest can legally apply to hot-path-decoded surfaces that zstd
             is currently banned from. Two concrete targets: (1) chunks_canonical/text when
             nest-runtime materialize() reads it per query -- GB/s lz4 decode makes
             'always-compressed text' viable without per-citation latency; (2) a future
             lz4-framed transparent layer over int8 embeddings where the runtime decodes a 64KB
             block into a small scratch buffer just-in-time before the SIMD dot product, since
             the branch-light wildcopy is cheap enough to amortize against the AVX2/NEON kernel
             cost -- the only realistic path to compressing embeddings (today raw/f16/int8 only)
             without breaking 'scored directly from mmap.' Also steal the LSIC add-255 varint
             and the frozen end-of-block invariants pattern for nest's own section-length and
             manifest varints (byte-granular, zero bit-shift, deterministic). Respect
             constraints: each codec file <=300 lines, typed thiserror errors, no panics; the
             format's repr-stable, little-endian, byte-aligned nature matches nest's repr(C) +
             LE rule exactly.
compression: Indirect but strategic. lz4 LOSES to zstd on raw ratio, so it does not advance the 'compress
             more than everyone' headline on cold sections. Its relevance is unlocking
             compression on surfaces nest currently leaves uncompressed because the decode
             budget is too tight: embeddings (hot SIMD path) and per-citation text
             materialization. A GB/s-class, mmap-friendly, allocation-free codec is the
             prerequisite for ever compressing those, widening the set of compressible bytes
             even if each byte compresses less than under zstd.
perf:        Default ~780 MB/s compress at ~2.1x ratio; LZ4_HC ~41 MB/s compress at ~2.72x ratio;
             decompression multiple GB/s per core (often 4-5 GB/s), frequently
             RAM-bandwidth-bound. Decode has no entropy stage, is allocation-free and
             branch-light; wildcopy needs output-buffer over-allocation slack (copies in 8-byte
             chunks). xxHash-32 in the frame layer is a fast non-cryptographic checksum (not a
             substitute for nest's four SHA-256 surfaces, but a useful cheap per-block guard if
             nest ever streams sub-section blocks).
