RustCrypto/hashes
category: hashing-crypto   |   steal priority: HIGH

siblings: ./00-index.txt   |   map: ../../README.txt

what:        A pure-Rust collection of cryptographic hash crates (sha2, sha3, blake2, blake3 via
             traits-preview, ripemd, etc.) unified under the `digest` crate's
             `Update`/`FixedOutput`/`ExtendableOutput` traits, with the heavy backends doing
             runtime-dispatched hardware acceleration (x86 SHA-NI, AArch64 sha2 extension, AVX2,
             NEON, WASM simd128) over a shared `block-buffer` block-accumulation abstraction.
innovation:  A single small trait surface (`Digest` = `Update` + `FixedOutput` + `Reset`, plus
             `ExtendableOutput`/`XofReader` for variable-length output) lets you write integrity
             code generically over any hash, while the concrete crate transparently selects the
             fastest CPU backend at runtime via the `cpufeatures` zero-sized-token model - so
             hashing becomes hardware-accelerated for free without the format ever naming a
             backend. The block-buffer abstraction cleanly separates "accumulate input into
             fixed compression blocks" from "compress a block," which is exactly the pattern
             nest's domain-separated, length-prefixed chunk_id preimage already imitates by
             hand.
techniques:
  - digest trait split: Update (streaming input) + FixedOutput (finalize) + Reset +
    ExtendableOutput/XofReader for XOF, enabling generic-over-hash code
  - cpufeatures runtime CPU detection via a zero-sized token type (cpufeatures::new!) that gates
    SHA-NI / sha2-ext / AVX2 / NEON / simd128 backends with soft fallback, no_std-friendly
  - sha2 0.11 multi-backend cfg system: sha2_backend / sha2_256_backend override flags, plus
    soft 'compact' vs unrolled for binary-size vs speed tradeoff
  - block-buffer: accumulate arbitrary-length input into fixed compression-function blocks (64B
    for sha256), decoupled from the compression kernel
  - BLAKE3 Merkle-tree hashing: 1024B chunks, 64B blocks, 32B chaining values; tree shape
    enables SIMD-parallel and rayon multithreaded hashing of large inputs
  - BLAKE3 verified streaming: independently verifiable subtree chaining values let you
    authenticate a byte range without rehashing the whole input
  - BLAKE3 XOF: finalize_xof() -> OutputReader (Read+Seek) for arbitrary-length random-access
    keyed output; one primitive for hash, MAC (keyed_hash), and KDF (derive_key)
  - domain-separated + length-prefixed preimage construction to make hashes collision-safe
    across concatenated fields (nest already uses this in chunk_id)
nest steals: nest-format already depends on sha2 = "0.11" and calls Sha256::digest/Update across exactly the
             right five places: header.rs (header_checksum), section_entry.rs (per-section
             checksum), footer.rs (file_hash), reader/decode.rs (content_hash), and chunk.rs
             (chunk_id). Three concrete steals: (1) Confirm/enable sha2's default
             runtime-dispatch backends so file_hash over the whole pre-footer body and
             per-section checksums get x86 SHA-NI / AArch64 sha2-ext acceleration for free on
             the validate path - pure additive, no format change, just verify no
             `sha2_backend="soft"` override and that 0.11 auto-detection is on; speeds up
             `validate` and build determinism checks. (2) Add a tiny internal Hasher abstraction
             in nest-format (new ~80-line src/hashing.rs, single-responsibility, under the
             300-line cap) wrapping `impl digest::Update + FixedOutput` so all four integrity
             surfaces share one domain-separated builder instead of five hand-rolled call sites
             - reduces drift, makes the preimage spec auditable in one file. (3) For the
             content-addressing roadmap (graph search, dataset/repo/binary-blob compression,
             audio/video), evaluate BLAKE3 (blake3 crate, traits-preview) as an OPTIONAL
             additive hash-id scheme for large blobs: its Merkle-tree gives SIMD+rayon-parallel
             hashing of multi-GB inputs and verified-streaming of byte ranges, mapping onto
             nest://content_hash/chunk_id range reopen - but it must be a new version-tagged
             digest algorithm (the sha256: prefix in chunk_id stays the v1 default) to preserve
             determinism and the FROZEN v1 format.
compression: Indirect but real. Hashing is not an entropy coder, so it does not shrink bytes; its relevance
             to 'compress more than everyone' is (a) making the four integrity surfaces cheap
             enough that nest can hash aggressively-compressed/deduplicated content on every
             build and validate without becoming a bottleneck, and (b) BLAKE3's
             verified-streaming + content-addressing enabling block-level dedup across
             datasets/repos/whole-databases (identical subtrees hash identically), a
             prerequisite for cross-document deduplication that actually drives corpus-level
             compression. Hardware-accelerated SHA-256 keeps deterministic reproducible builds
             fast as corpora grow.
perf:        sha2 0.11 default = runtime dispatch: SHA-256 uses x86-sha (SHA-NI) or aarch64-sha2 extension
             (~2x soft on SHA-NI CPUs, far more vs naive); SHA-512 uses AVX2 / aarch64-sha3.
             soft backend unrolls rounds by default (faster, bigger binary); 'compact' cfg
             trades speed for size - relevant to nest-python abi3 cdylib and CLI footprint.
             block-buffer works in 64B blocks for sha256. BLAKE3 is 5-10x faster than SHA-256 on
             non-SHA-NI CPUs (~2x even with SHA-NI), SIMD across
             SSE2/SSE4.1/AVX2/AVX-512/NEON/WASM with rayon multithreading; its update() only
             reaches full SIMD width with >=16 KiB buffers (8 KiB hits AVX2 but not AVX-512) -
             feed it large mmap slices, not small chunks. cpufeatures detection is one-time and
             effectively zero-cost after init.
