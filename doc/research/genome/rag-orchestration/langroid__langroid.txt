what:        A Python multi-agent LLM framework whose DocChatAgent implements a RAG retrieval pipeline that
             fuses semantic + BM25 + fuzzy rankings via Reciprocal Rank Fusion (c=60), then
             applies deterministic post-rank reordering (diversity, lost-in-middle periphery)
             and optional cross-encoder/LLM relevance extraction.
innovation:  Rank-only Reciprocal Rank Fusion as the hybrid-search combiner: scores from heterogeneous
             retrievers are discarded and replaced by 1/(rank_i + 60) summed across methods.
             Because it consumes only ordinal rank, it fuses score spaces that are not
             comparable (cosine vs BM25 vs edit-distance) with zero normalization, zero tuning,
             and is fully deterministic given deterministic input rankings -- exactly what nest
             already guarantees for its hnsw and bm25 indices.
techniques:
  - Reciprocal Rank Fusion: combined = sum_methods 1/(rank + c), c=60.0, sort desc; rank-only so
    no score normalization needed
  - Three-way fusion of semantic(vector) + BM25Okapi + fuzzy(thefuzz partial_ratio) rankings
    rather than the usual two-way
  - rank_to_periphery: deterministic anti-'lost-in-middle' reorder splitting by index into odds
    + reversed(evens) so top hits land at both list ends (1..9 => 1 3 5 7 9 8 6 4 2)
  - rank_with_diversity: greedy MMR-style selection picking the passage with min mean cosine
    similarity to already-selected set
  - n_neighbor_chunks context-window expansion via stored window_ids metadata: re-stitch
    adjacent original chunks around a hit
  - cross-encoder rerank with logistic squashing 1/(1+exp(-score)) using ms-marco-MiniLM-L-6-v2
    (mutually exclusive with RRF)
  - RelevanceExtractorAgent: LLM extracts verbatim relevant sentences by numbering, returns
    NO_ANSWER when nothing matches (post-retrieval filter)
nest steals: nest-runtime/search: nest already runs hnsw + bm25 and fuses bm25 via reciprocal-rank fusion
             before the mandatory exact-cosine rerank. Steal two concrete upgrades. (1)
             Generalize the RRF fuser in the hybrid path to a rank-only sum_methods 1/(rank+60)
             over N>=2 ordered lists with c exposed in the search_contract section of
             nest-format (additive, no version bump), so a future third signal
             (fuzzy/edit-distance term match, helping the known CJK/thai bm25 gap) drops in
             without touching the codec; keep determinism via the existing alphabetical/seeded
             ordering. (2) Add rank_to_periphery as a pure-integer, deterministic final reorder
             in nest-runtime::search::materialize (odds + reversed(evens)) -- ~15 lines, no ML,
             no float, panic-free, well under the 300-line file cap -- improving downstream LLM
             answer quality on the returned chunk list at zero index/storage cost. The
             n_neighbor_chunks idea maps directly onto nest's chunks_original_spans: store
             left/right neighbor chunk_ids so a hit can re-materialize its original window from
             the mmap.
compression: Low-to-none for raw byte compression: langroid has no on-disk format, entropy coder, or
             quantization -- it is an orchestration layer that outsources storage to
             Qdrant/LanceDB/Chroma. Indirect relevance: the n_neighbor_chunks/window_ids pattern
             argues for storing only neighbor chunk_id pointers (a few varints) instead of
             duplicating overlapping context text, which trims redundancy in chunks_canonical
             and supports nest's 'compress more than everyone' goal by deduplicating chunk
             overlap.
perf:        All steal-worthy pieces are cheap: RRF is O(total_hits) integer/float adds; rank_to_periphery is
             an O(k) index permutation with no allocation beyond the output vec; both run after
             the hot-path exact-cosine rerank, so they add negligible latency and are
             SIMD-irrelevant. langroid itself is pure Python with per-method latency dominated
             by network calls to external vector DBs and LLM relevance extraction (the
             relevance_extractor adds an LLM round-trip per passage and is the main latency
             sink, defaultable to None) -- nest gains the math, not the runtime cost.
