what:        Jina is a gRPC/HTTP/WebSocket microservice framework for multimodal AI serving whose real
             reusable asset is its data layer DocArray, with a columnar DocVec store that stacks
             all per-document tensors into one contiguous tensor and serializes via a typed
             protobuf schema (DenseNdArrayProto = raw buffer bytes + shape + dtype).
innovation:  The DocVec columnar layout: instead of storing N documents row-wise (each carrying its own
             embedding object), DocVec transposes the array so every schema field becomes a
             column, and all tensor fields across documents are stacked into ONE contiguous
             backing tensor; each Document becomes a zero-copy view (like tensor[i]) into that
             column. This is exactly nest's "embeddings as one packed matrix scored straight off
             mmap" idea, generalized into a data model with a typed protobuf wire format
             (DenseNdArrayProto: bytes buffer + repeated uint32 shape + string dtype) that
             cleanly separates the dense numeric payload from its shape/dtype metadata.
techniques:
  - DocVec columnar transpose: per-field columns, all tensor fields stacked into one contiguous
    tensor for batch/SIMD-friendly access
  - Document-as-view: BaseDoc holds no data, it is a numpy/torch-style view[i] into the shared
    column buffer (zero-copy slicing)
  - DenseNdArrayProto encoding: split tensor into raw `bytes buffer` + `repeated uint32 shape` +
    `string dtype`, decoupling dense payload from metadata
  - DocVecProto with 4 typed column maps (tensor_columns / doc_columns / docs_vec_columns /
    any_columns) routing dense tensors, nested docs, doc-arrays, and heterogeneous scalars to
    format-appropriate codecs
  - Deferred tensor backend selection: dtype/shape metadata lets the same bytes deserialize to
    numpy/torch/tf at read time without re-encoding
  - Pluggable protocol x compression matrix (protobuf|pickle) x (lz4|bz2|lzma|zlib|gzip) via
    self-describing `name.$protocol.$compress` filenames
  - Recursive nesting: a BaseDoc field becomes a nested DocVec column, enabling columnar storage
    of structured/multimodal records
nest steals: Two concrete adaptations. (1) nest-format: adopt DenseNdArrayProto's split-metadata discipline
             for any future non-embedding tensor section (image-similarity feature matrices,
             audio frames) -- store raw little-endian buffer + explicit (shape,
             dtype/encoding-id) descriptor in the section manifest, never interleaving metadata
             into the hot dense bytes; this keeps the AVX2/NEON dot-product kernel pointed at a
             clean contiguous matrix like nest's existing embeddings section, and the
             deferred-backend trick maps onto nest's float16/int8 encoding ids (same bytes,
             reader picks decode path). (2) nest-format sections + manifest: borrow DocVec's
             4-way column routing as the design rule for the planned multi-modal expansion
             (text/json/yaml/parquet/pdf/audio/video) -- a typed-column manifest where each
             logical column declares its codec (zstd for text/json columns, raw-mmap
             f32/f16/int8 for dense tensor columns, bm25 for tokenized text), so the writer
             routes each column to its best codec while the reader still mmaps tensor columns
             directly. This is the columnar analogue of nest's current per-section encoding,
             uses RESERVED section ids 0x09+ additively, and unlocks "compress structured
             datasets/parquet/repos" without breaking single-file/offline/deterministic
             guarantees. nest-runtime hot path is untouched because tensor columns stay raw
             contiguous f32/f16/int8.
compression: Medium-indirect. Jina/DocArray does NOT do extreme compression -- embeddings hit the wire as a
             raw f32 buffer (DenseNdArrayProto.buffer), and "compression" is just an outer
             general-purpose codec pass (lz4/zlib/lzma) over the serialized blob, the opposite
             of nest's policy of never general-compressing embeddings. The transferable
             compression-relevant idea is structural, not entropic: the columnar transpose
             groups like-typed, like-dtype values together, the precondition for high-ratio
             compression of NON-embedding data (delta/dictionary/RLE on an id column, zstd on a
             homogeneous text/json column) and for keeping dense tensor columns in one clean
             contiguous block that int8 quantization and mmap-scoring exploit. Informs nest's
             dataset/parquet column-compression roadmap; offers no new entropy coder.
perf:        DocVec's contiguous column tensor is built for batch inference and vectorized ops -- the same
             memory shape nest relies on for SIMD dot products; zero-copy Document views avoid
             per-doc allocation. DocArray got ~240% faster JSON serialization by moving the
             validation core to Pydantic v2 (Rust pyo3), confirming the
             build-in-python/serve-in-Rust split nest already uses via nest-python.
             Jina/DocArray ships no SIMD distance kernels of its own; vector search is delegated
             to external Document Indexes (HNSWLib/Qdrant/Weaviate/Elastic), so there is nothing
             to steal on the ANN/SIMD side -- nest's hand-rolled HnswIndex + mandatory exact
             cosine rerank is already ahead.
