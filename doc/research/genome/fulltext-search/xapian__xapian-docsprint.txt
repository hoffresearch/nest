what:        The docsprint repo is only the Sphinx user-guide source for Xapian, a mature C++ probabilistic
             IR engine whose real value here is its documented glass backend on-disk format:
             chunked, delta+varint-encoded BM25 posting lists with a separated document-length
             stream and order-preserving numeric encodings.
innovation:  Decouple per-posting payload from the inverted list: store docids as varint deltas inside
             fixed-key chunks, and crucially do NOT repeat document length in every posting
             entry -- keep document lengths in one separate compressed stream indexed like a
             posting list. nest currently has no such separation and can shrink its bm25_index
             section dramatically by adopting it.
techniques:
  - chunked posting lists: each term's list split into B-tree chunks keyed by
    pack_string_preserving_sort(term)+pack_uint_preserving_sort(first_docid) so chunks sort and
    allow skip-ahead
  - docid delta encoding inside a chunk: store (next_docid - prev_docid - 1) instead of absolute
    ids, plus per-posting wdf
  - pack_uint variable-byte (7-bit continuation) integer codec; redundant encodings deliberately
    left to encode runs of equal-wdf docids compactly
  - separated document-length stream: doclen stored once per doc in its own postlist-like
    structure, never repeated per term-posting
  - sortable_serialise / pack_uint_preserving_sort: encode ints and IEEE doubles to byte strings
    whose bytewise order equals numeric order, enabling range filters and sorted scans without
    decoding
  - prefix compression within value chunks: store count of shared-prefix bytes with previous
    entry instead of full value
  - weight-tiered posting-list splitting (matcher optimization): partition postings into
    high/low BM25-weight tiers so top docs are read first -- requires freezing k1/b at index
    time
  - out-of position encoder + separate position table: term positions stored relative to a known
    max in a dedicated table, off the scoring hot path
nest steals: Target nest-format's bm25_index section (0x08) and nest-runtime bm25::Bm25Index. (1) Restructure
             on-disk postings to varint-delta docids per term with a SEPARATE doclen stream
             rather than embedding doclen per posting -- biggest size win, fits nest's additive
             format (new internal layout inside an existing reserved-payload section, no version
             bump). (2) Add a small order-preserving varint codec (pack_uint_preserving_sort
             analogue) in nest-format/encoding so the bm25 term dictionary and numeric metadata
             are byte-sortable and range-scannable straight off mmap, reinforcing the
             deterministic alphabetical-term-order rule already in place. (3) Adopt prefix
             compression for the alphabetically-sorted term dictionary (store shared-prefix
             length vs previous term) -- nearly free since terms are already sorted, helps
             'compress more than everyone'. (4) Optionally add weight-tiered split as
             early-termination for bm25, only under a frozen-params contract consistent with the
             deterministic search_contract and mandatory exact rerank. Keep all of this on the
             cold/text path only -- embeddings stay raw f32 for SIMD scoring per nest's hot-path
             rule.
compression: Direct: separated-doclen-stream + delta-varint posting layout and sorted-term prefix compression
             are exactly the structural redundancy elimination that shrinks nest's bm25_index
             (0x08) without any entropy coder, complementing zstd-on-non-embedding-sections.
             Order-preserving encodings let compressed term dictionaries be searched without
             full decode, keeping the single-file mmap-and-scan model intact.
perf:        Glass optimizes for ascending-docid streaming reads (the matcher's access pattern); chunk
             skip-ahead via sortable first-docid keys avoids scanning whole lists.
             Prefix-compressed chunks need linear decode within a chunk but chunks are small so
             it is cheap. pack_uint trades a few wasted bits for branch-light decode. Maps
             cleanly onto nest's mmap-and-scan, no-server runtime; nothing requires a socket or
             background process, satisfying offline-by-construction.
