what:        A Rust+WebAssembly static-site full-text search engine that builds a single self-contained
             binary `.st` index file (MessagePack-serialized inverted "prefix map") which a WASM
             blob loads in the browser to do instant prefix search with positional excerpt
             highlighting, no server.
innovation:  The entire search index is a single self-describing versioned binary artifact that bundles BOTH
             the inverted index AND the displayable content (excerpts + char offsets) so the
             search runtime needs nothing but the one file to return rendered, highlighted
             results offline. The index is keyed by BTreeMap<String, Container> (a "prefix map")
             where each Container is self-sufficient: from one container you derive every result
             for a query, and prefix queries with no exact container resolve through aliases
             (BTreeMap of alias-target -> score) that redirect to the nearest indexed term. The
             on-disk structure directly serves the query without a separate scoring pass over
             the corpus.
techniques:
  - Inverted index as BTreeMap<String, Container> 'prefix map' (deterministic, alphabetically
    ordered keys) instead of a hashmap, so iteration/serialization is stable
  - Self-contained Container: results: BTreeMap<EntryIndex, SearchResult> + aliases:
    BTreeMap<AliasTarget, Score>, so prefix/partial matches alias to indexed terms with a
    discounted score
  - Excerpts stored INLINE in the index with word offset, field (title vs contents), and
    char-range annotations, so the runtime returns ready-to-render highlighted snippets without
    touching original documents
  - MessagePack binary serialization via rmp-serde (compact tag-length-value, no JSON key
    repetition) for the .st payload
  - Self-describing versioned container: length-prefixed version string (e.g. 'stork-3.0.0')
    precedes payload; VersionedIndex::try_from dispatches to V2/V3 parsers for additive format
    evolution
  - Scoring via MATCHED_WORD_SCORE base plus configurable title_boost multiplier and
    exact-vs-prefix discount, precomputed at build time and stored, not recomputed at query time
  - rust-stemmers (Snowball) + unicode-segmentation + stopword normalization at BUILD time so
    query-time matching is cheap and the index conflates 'tries'->'try', 'Power'->'power'
  - excerpts_per_result=0 build switch that strips inline excerpts to shrink the index 20-50%
    (filter-only mode), trading display payload for size
nest steals: Three steals for nest-format's optional bm25_index section (0x08). (1) Adopt Stork's
             BTreeMap<term, Container> postings layout: nest already mandates 'bm25 alphabetical
             term order' for determinism, so a BTreeMap-backed self-contained per-term container
             is a drop-in that satisfies determinism by construction and serializes stably. (2)
             Adopt the alias/prefix-redirect trick in nest-runtime/bm25 to add cheap prefix and
             stemmed-variant matching to nest's word-segmented tokenizer (a known gap) without
             storing full substring postings: store only canonical terms plus an alias table
             mapping prefixes/stems to canonical term ids with a discount score; this directly
             mitigates nest's CJK/Thai tokenizer degradation by letting non-exact segments alias
             to the nearest indexed term. (3) Precompute per-doc term scores (Stork's build-time
             MATCHED_WORD_SCORE + boost model) so the bm25 candidate pass in nest-runtime is a
             pure lookup before the mandatory exact-cosine rerank, keeping the hot path
             allocation-light. Keep nest's own serialization (repr(C), little-endian, zstd on
             non-embedding sections) -- borrow the data-structure shape, NOT rmp-serde. For
             extreme compression: Stork's excerpts_per_result=0 'filter-only index' maps to a
             nest preset flag that drops any cached snippet/offset payload from bm25_index and
             reconstructs spans on demand from chunks_original_spans, shrinking the optional
             section 20-50% while citations stay intact.
compression: Indirect but real for nest's bm25 section, not the embedding hot path. Two transferable size
             ideas: (a) the alias/prefix-redirect table avoids materializing substring/prefix
             postings (Stork's docs note full substring indexing bloats the file), giving prefix
             search at a fraction of postings size; (b) the excerpts_per_result=0 'strip display
             payload, keep only the filter' mode is a clean precedent for a nest preset that
             drops cached snippets and reconstructs spans from chunks_original_spans, a 20-50%
             cut on bm25_index. Stork's actual codec (MessagePack, no entropy coder, no
             compression crate -- relies on the host server's gzip) is BELOW nest's bar: nest
             already zstd-compresses non-embedding sections, which beats raw MessagePack, so
             nest should NOT adopt rmp-serde. Borrow index shape and the two size tricks; nest's
             existing zstd + repr(C) encoding dominates Stork's on-disk format.
perf:        Stork's claim to fame is sub-millisecond browser-side search by loading the whole index into
             WASM linear memory and doing direct BTreeMap lookups (O(log n) key lookup +
             container iteration), no network round-trips after the initial index download. No
             SIMD, no bitpacked postings, no roaring bitmaps -- deliberately simple: build-time
             precomputation (stemming, scoring, excerpt extraction) trades index size for
             query-time CPU. Entire index resident in WASM heap, which is why >~megabyte corpora
             and <3-char queries get slow and the 2.0 line moved to sharded indexes (load one
             chunk at a time) to bound resident memory. Lesson for nest: precompute at build,
             keep the query path a pure lookup; but Stork's lack of bitpacked/delta-encoded
             postings is exactly where nest can do better.
