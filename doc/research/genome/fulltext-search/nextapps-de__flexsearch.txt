what:        An in-memory full-text search library whose "contextual index" replaces query-time TF-IDF with a
             pre-scored lexical dictionary that buckets postings by an integer relevance score
             (resolution), making multi-term intersections near-constant-time.
innovation:  Pre-score at index build, not query time: instead of storing one posting list per term and
             computing BM25/TF-IDF on the fly, FlexSearch stores `map[score_bucket][term] =
             [doc_ids]` where the bucket index IS the quantized relevance. Relevance is
             collapsed into a small integer in [0, resolution) computed from three distances
             (document position, partial/token distance, and contextual term-pair distance
             within a bidirectional window of depth d). Querying becomes: walk buckets from
             highest score to lowest and intersect/union the small doc-id arrays, so scoring is
             "already done" and ranking is just bucket order. This trades a tiny, bounded score
             space for eliminating per-hit float math, and it makes the score field itself
             compressible (a 4-bit/1-byte ordinal instead of an f32).
techniques:
  - Resolution-bucketed inverted index: term -> array of `resolution` buckets, each holding
    doc-id lists; bucket index = quantized integer relevance (default resolution 9), so score is
    an ordinal not a float
  - Contextual pre-scoring: bidirectional moving 2-pointer window of configurable `depth`
    pre-computes term-pair proximity scores at build time; bidirectional flag collapses
    (a,b)/(b,a) pairs to halve memory
  - Three-distance scoring model (document distance + partial distance + contextual distance)
    deliberately replacing TF-IDF, yielding an integer score
  - complexity = resolution - threshold: a `threshold` floor prunes low-score buckets entirely
    from storage and from intersection, bounding both index size and query cost
  - Latin encoder ladder (Exact -> Normalize -> Balance -> Advanced -> Extra -> Soundex) giving
    ~7% to ~70% term-dictionary shrinkage via progressive phonetic normalization, collapsing
    many surface forms to one key
  - Tokenizer memory-factor taxonomy (strict 1x, forward nx, reverse 2n-1x, full n(n-1)x,
    tolerant 2(n-2)+2x) making the size/recall tradeoff explicit and selectable
  - fastupdate secondary register for O(1) delete via reverse doc->term map, plus cleanup() to
    compact empty slots
  - Fast-boot serialization: export/import the already-pre-scored dictionary so rehydration does
    zero recompute
nest steals: Apply to nest-runtime crates/nest-runtime/src/bm25 (index.rs + codec.rs) and section 0x08. (1)
             CODEC WIN, additive: today codec.rs writes `Posting{doc:u32, tf:u32}` (8
             bytes/posting) and search.rs recomputes BM25 floats at query time. Adopt
             FlexSearch's bucketing: precompute each posting's BM25 contribution at build time,
             quantize it into N ordinal buckets (e.g. 16, 4 bits), and store the inverted list
             grouped by bucket. The 4-byte tf becomes a 4-bit ordinal, shrinking section 0x08
             roughly 30-40%, and doc-id lists per bucket are monotonically sortable so they
             zstd-delta-compress far better than interleaved (doc,tf). This stays within the
             0x08 section and is gated by BM25_PAYLOAD_VERSION (bump the payload version, not
             NEST_FORMAT_VERSION, since 0x08 is optional and additive). (2) SPEED WIN: search
             becomes bucket-descending iteration with early termination once top-k is filled
             from high buckets, removing the per-posting idf/denom float loop in
             index.rs:106-114; nest's mandatory exact-cosine rerank then dominates less. Keep
             determinism via alphabetical term order (already done) plus fixed bucket
             boundaries. (3) TOKENIZER/CJK GAP: port the Latin normalization ladder into
             bm25/tokenize.rs as deterministic encoder presets (raw -> normalize-diacritics ->
             phonetic) to collapse surface forms and shrink the term dictionary; this directly
             attacks the documented bm25 tokenizer gap. (4) RRF fusion in fusion.rs already
             wants ranks, not raw scores, so an ordinal bucket score is a natural fit. Optional
             `context.depth` proximity could later be a reserved 0x09+ section.
compression: Directly relevant. Quantizing the per-posting score from an f32/u32 into a small integer ordinal
             (resolution buckets) is the same move nest already makes for embeddings (f32 ->
             int8); applied to the bm25 0x08 section it cuts posting size ~30-40% before zstd,
             and grouping doc-ids by bucket produces monotonic, delta-friendly runs that zstd
             compresses much better than interleaved (doc,tf) pairs. The threshold prune further
             shrinks the index by dropping low-relevance postings entirely. This advances the
             north-star "compress more than everyone" on the lexical-index section specifically,
             with no recall loss on the top buckets and the exact-cosine rerank still
             guaranteeing real scores.
perf:        FlexSearch reports ~50M single-term queries/sec vs 3.9k-23k for competitors, attributed entirely
             to pre-scored buckets eliminating query-time scoring and shrinking intersection
             sets. Memory scales mainly with context depth (depth 1 ~12.5MB, depth 2 ~21.5MB on
             Gulliver's Travels corpus); bidirectional pair-collapsing reduces it (17.9MB vs
             19.0MB at depth 2). Pure JS, single-thread hot path, with optional Web Worker
             sharding. For nest the relevant takeaway is that ordinal scores make both storage
             smaller and the scan branch-predictable; no SIMD needed since the hot path becomes
             integer bucket iteration plus sorted-list intersection.
