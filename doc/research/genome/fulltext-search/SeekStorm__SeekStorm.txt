what:        A sub-millisecond, sharded, real-time full-text + vector search engine in Rust (Apache-2.0)
             whose lexical core stores posting lists as roaring-bitmap-compressed doc-id sets
             with delta+VINT-encoded term positions, ranked by BM25F/BM25F_Proximity via
             Document-at-a-Time traversal with improved Block-Max WAND, MaxScore, galloping and
             SIMD set intersection, served from one on-disk format in either RAM or mmap mode.
innovation:  A production lexical index whose byte layout is identical in RAM and on mmap'd disk (switchable
             via an AccessType flag), so the inverted index is served straight off the file
             exactly like nest's embeddings already are. The winning combination of
             compact-AND-fast: roaring-bitmap posting lists (doc-id sets) + a separate
             delta-compressed VINT position stream + Block-Max WAND skip metadata, traversed
             Document-at-a-Time so no large intermediate result sets ever materialize.
techniques:
  - Roaring bitmaps for posting lists: per-65536-doc-chunk hybrid array/bitmap/run containers,
    giving compressed doc-id sets that allow hardware SIMD AND/OR directly on the compressed
    form (no full decode)
  - SIMD vector intersection and union of compressed bitmap posting lists on both x86-64 (AVX2)
    and AArch64 (NEON), the same two-arch dispatch nest already runs for dot products
  - Galloping (exponential) intersection for skewed posting-list size ratios, complementing SIMD
    merge for balanced lists
  - Improved Block-Max WAND + MaxScore: per-block max-impact upper bounds let top-k pruning skip
    whole blocks whose best possible BM25 cannot enter the heap
  - Document-at-a-Time (DAAT) traversal scoring one doc fully across all query terms, bounding
    memory vs Term-at-a-Time accumulators
  - Term positions delta-compressed then VINT (variable-byte) encoded as a SEPARATE stream from
    doc-ids, enabling phrase/proximity (BM25F_Proximity) without bloating the doc-id bitmaps
  - Zstandard-compressed JSON document store (docstore.bin) decoupled from index files
    (index.bin doc-ids+positions, index.json meta, delete.bin tombstones)
  - Tombstone-based real-time delete (delete.bin, recoverable until compaction) so every doc is
    searchable immediately, before/during commit
nest steals: nest already ships an optional bm25_index section (0x08) in nest-runtime::bm25::Bm25Index. Steal
             three layers into it additively (0x08 internals can evolve without a
             NEST_FORMAT_VERSION bump): (1) in nest-format/src/sections + encoding, replace any
             plain doc-id list inside 0x08 with roaring-bitmap-encoded posting lists plus a
             SEPARATE delta+VINT position stream; this is the single biggest size win for the
             lexical section and keeps it serveable straight off mmap, matching nest's
             read-from-disk discipline. (2) in nest-runtime::bm25, add Block-Max WAND + MaxScore
             top-k pruning with per-block max-impact bounds stored alongside each posting list;
             this slashes query cost and is safe because bm25 only needs to surface candidates
             for reciprocal-rank fusion before nest's mandatory exact-cosine rerank. (3) reuse
             nest-runtime's EXISTING simd dispatcher (AVX2/NEON/scalar) for bitmap AND/OR
             intersection, so adding integer set-ops is incremental, not a new subsystem.
             Preserve determinism by keeping alphabetical term order and a single non-sharded
             global-stats index. The zstd JSON docstore maps onto nest's already-zstd-encoded
             chunks_canonical, so that piece is already solved and serves only as validation.
compression: Directly on-mission for "compress more than everyone" on the lexical/text path. Roaring bitmaps
             are a near-optimal compressed encoding for sparse-to-dense doc-id sets (array
             containers for sparse terms, bitmap for dense, run containers for contiguous runs)
             and routinely beat plain VINT/delta posting lists while STILL supporting SIMD set
             ops without full decode, so compression and serve-speed are not in tension, exactly
             nest's requirement. The separate delta+VINT position stream keeps proximity ranking
             from inflating the doc-id bitmaps. For nest's bm25_index (0x08) this is the
             highest-leverage size reduction for the text index, complementing (not touching)
             the embeddings hot path which stays raw f32/f16/int8 for direct SIMD scoring.
perf:        Claims sub-millisecond queries and ~20x Lucene throughput; reported ~40,000 docs/sec indexing on
             5M-doc Wikipedia, and 4-6x faster indexing / 3x shorter query latency from
             intra-query shard parallelism. SIMD intersection runs on x86-64 AVX2 and AArch64
             NEON, the same targets nest already supports. Index latency and size grow linearly
             with doc count while RAM stays roughly constant in mmap mode, enabling
             billion-scale indices. nest should take the per-document deterministic single-index
             path, not the shard topology.
license:     Apache-2.0 (permissive). Roaring bitmap is itself a published standardized format with
             permissive Rust crates (e.g. roaring-rs), so nest can reimplement or vendor without
             GPL contamination. WARNING: do NOT adopt SeekStorm's sharding; it makes BM25 scores
             non-deterministic and non-comparable across shards (per-shard avg doc length, df,
             posting-list length, load-balanced non-deterministically), which would break nest's
             byte-identical reproducible builds. Keep a single deterministic index with global
             stats and alphabetical term order; steal the encoding, pruning, and SIMD set-ops
             only.
