what:        A Lucene-class Rust full-text search library whose inverted index stores posting lists as
             interlaced 128-doc blocks of delta-encoded, SIMD-bitpacked doc ids and bitpacked
             term frequencies, fronted by an FST term dictionary and a Block-Max-WAND skip list.
innovation:  128-doc block posting lists with delta+SIMD-bitpacking and a Block-Max-WAND skip list, fronted
             by an FST term dictionary.
techniques:
  - 128-doc block posting layout: delta+bitpacking on doc ids, bitpacking on term frequencies,
    interlaced to avoid pointer chasing
  - minimal per-block bit-width b = ceil(log2(max+1)); value = min + fetch_bits(num_bits*i..)
  - VInt fallback for the incomplete trailing block (1-127 docs)
  - SIMD bitpacking (BitPacker4x SSE3 128-int, BitPacker8x AVX2 256-int, scalar fallback) at
    ~5-7 billion int/s
  - FST term dictionary (BurntSushi fst): term -> TermOrdinal, ordinal mod block size locates
    one TermInfo block to decode
  - skip list with per-block fieldnorm_id + max_term_freq enabling Block-Max-WAND top-k pruning
  - fast-field columnar codecs: bitpacking + GCD divisor + linear/blockwise-linear interpolation
    over a min_value baseline
  - LZ4/Zstd block-compressed document store kept separate from the index
nest steals: Rewrite nest-runtime/src/bm25/codec.rs (and the Posting/TermEntry model in index.rs) to replace
             the current raw fixed-width u32 (doc, tf) pair encoding with tantivy-style 128-doc
             blocks: per term, delta-encode the already-doc-sorted posting doc ids and bitpack
             at minimal per-block width, bitpack the parallel tf block, and VInt the trailing
             partial block. This is a pure section-0x08 payload codec change behind
             BM25_PAYLOAD_VERSION (bump it; section id and additive v1 format are untouched), so
             it respects the FROZEN container. Term order stays alphabetical (already
             deterministic) -- optionally front the term-string region with an fst-crate FST to
             shrink it and get prefix lookups. Keep a scalar bitpacking kernel in
             nest-runtime/src/simd to honor the offline/repr(C)/LE/no-panic constraints (only
             vendor the bitpacking crate if its scalar fallback is acceptable). Add a per-block
             max_term_freq plus doc_length-derived bound to enable Block-Max-WAND in
             bm25/index.rs::search, cutting the full-posting scan that today touches every
             Posting. Keep files under the 300-line cap by leaving the block codec in codec.rs
             and putting WAND in a new wand.rs.
compression: High and direct. Today nest spends a flat 8 bytes per posting (u32 doc + u32 tf) plus u32
             doc_lengths, the dominant cost in the bm25_index section. Delta+bitpacking
             typically collapses doc ids to 4-8 bits each on dense corpora and tf to 2-4 bits
             (most tf are 1-2), a 4-8x shrink of the dominant posting array, advancing the
             'compress more than everyone' north star for the hybrid/tiny presets. The zstd
             wrapper over the now-bitpacked section adds little extra -- bitpacked integers are
             already near entropy-optimal, so this is real structural compression, not just a
             general codec pass.
perf:        bitpacking crate hits ~5.3-7 billion int/s compress and ~5.5-6.5 billion int/s decompress
             (SSE3/AVX2); delta decode ~5 billion int/s. A scalar fallback exists and is
             selected at runtime, so determinism + portability hold (nest can ship a scalar
             kernel matching its existing SIMD-dispatch pattern). Block-Max-WAND turns BM25 from
             O(all postings) into early-terminating top-k, helping amortize the ~300-500ms
             search-text python boot overhead by making the scan negligible. Bitpacked blocks
             decode straight off mmap (fetch_bits over a block) with no per-value branching,
             matching nest's mmap-and-score hot path.
