what:        Deep Lake is a columnar "tensor storage format" data lake that stores ML data as chunked,
             natively-compressed arrays and keeps a separate, run-length-encoded triplet of
             index maps (ChunkIdEncoder, BytePositionsEncoder, ShapeEncoder) mapping each sample
             index to its chunk, byte range, and shape without loading the bulk payload.
innovation:  Sidecar index maps are stored as 2D integer arrays of "runs" where each row holds a value plus
             the CUMULATIVE last-sample-index that run covers; consecutive identical values
             (same chunk, same shape, same per-sample byte size) collapse into a single row, and
             lookups are a binary search over the cumulative-index column. This run-length +
             cumulative-prefix-index hybrid makes per-sample sidecar metadata grow only when a
             value actually changes (a fixed-shape tensor of 1B samples needs one shape row;
             ~150MB chunk-id encoder per 1PB), while staying O(log n) random-addressable.
techniques:
  - Run-length + cumulative-index encoders: rows = (value, last_index_covered); identical
    consecutive samples collapse to one row
  - Binary search over the cumulative last-index column for O(log n) sample->location lookup
  - Triplet split of sidecar metadata: ChunkIdEncoder (sample->chunk), BytePositionsEncoder
    (per-sample byte size, offsets derived by prefix sum), ShapeEncoder (sample shape)
  - Metadata fully separated from bulk data so shape/offset queries never decode payload chunks
  - Native sample-level compression: store jpeg/png/mp4 bytes verbatim, copy-without-recode when
    raw codec matches tensor codec
  - Chunk-size bounds (lower/upper) packing variable-length samples into ~8MB chunks instead of
    static per-sample chunking
  - Tiling: samples larger than a chunk split across multiple chunks via a tile encoder
  - TQL + optimized hnswlib HNSW with exact linear-scan fallback under ~100k rows
nest steals: Adopt the run-length + cumulative-index encoder in nest-format for the chunks_original_spans
             (0x03) section and optionally chunk_ids (0x01). Today
             crates/nest-format/src/sections/spans.rs writes the full source_uri string plus two
             raw u64 (byte_start, byte_end) for EVERY chunk; when 5k chunks come from one
             document this is ~5k repeated URIs and ~80KB of offsets that are almost always
             contiguous (end[i]==start[i+1]). Replace with: (a) a deduplicated source_uri
             dictionary plus a per-chunk uri_id run-length encoded (one run per source
             document), and (b) delta/cumulative encoding of spans where contiguous chunks store
             only a run-length plus per-chunk length, reconstructing absolute offsets by prefix
             sum exactly like BytePositionsEncoder. This is an internal encoding of a
             non-embedding (cold-path) section, so it is zstd-eligible and never touches the
             SIMD scoring hot path. It fits the frozen v1 format as a NEW encoding id in the
             reserved 4-255 range (or a transparent re-encode within the existing section that
             decodes identically) with no NEST_FORMAT_VERSION bump. content_hash stays stable
             because it hashes DECODED canonical sections, and determinism holds via an
             insertion-stable dictionary. It shrinks provenance/spans metadata that currently
             scales O(num_chunks) with redundant strings, directly serving the
             compress-more-than-everyone north star.
compression: High. nest's metadata sections (spans, chunk_ids, provenance) currently scale O(num_chunks) with
             verbatim repeated source URIs and raw 8-byte offsets. The run-length +
             cumulative-index scheme collapses these to O(num_distinct_runs), often
             near-constant for single-document corpora, removing structural redundancy that zstd
             alone leaves on the table (entropy coding shrinks bytes but not the inherent
             redundancy of contiguous 64-bit offsets, which is better eliminated before
             compression). It targets exactly the non-embedding part of the .nest file,
             complementing int8/f16 embedding quantization.
perf:        Encoders are tiny: ~150MB ChunkIdEncoder per 1PB tensor; a fixed-shape tensor needs a single
             ShapeEncoder row. Lookups are O(log n) binary search over the cumulative column
             using only integer ops, with no payload decompression, so they stay off any SIMD
             hot path. For nest the span/uri encoder is read once during materialize/cite (not
             during scoring), so binary-search cost is irrelevant to query latency; the win is
             on-disk size plus faster section parse (fewer length-prefixed strings). Deep Lake's
             hnswlib HNSW handles ~35M embeddings in <1s with exact linear scan under ~100k
             rows, mirroring nest's mandatory-exact-rerank philosophy.
