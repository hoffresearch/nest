siblings: ./00-index.txt   |   map: ../../README.txt

what:        A multiprocess/multithreaded downloader that turns billion-scale image-URL lists into sharded
             WebDataset tar files paired 1:1 with lightweight columnar parquet sidecars and
             order-aligned embedding .npy arrays, all addressed by a deterministic positional
             composite key.
innovation:  The "shadow sidecar" split: heavy opaque payload (jpg bytes in tar) is stored separately from a
             parallel lightweight columnar metadata file (parquet) that mirrors it 1:1, so all
             filtering, statistics, and validation happen against the small columnar file
             without ever touching the heavy payload, while a deterministic positional composite
             key (SSSSSIIII = 5-digit shard id + 4-digit in-shard index) preserves exact order
             alignment across every parallel artifact (tar payload, parquet metadata, npy
             embeddings) and makes builds resumable.
techniques:
  - composite positional key SSSSSIIII: zero-padded shard-id prefix + in-shard index, encoding
    both location and order in a sortable integer string
  - 1:1 ordered alignment invariant: input urls -> tar payload -> parquet metadata -> npy
    embeddings all in identical sample order, addressable by offset
  - shadow columnar sidecar (parquet) mirrors heavy tar so stats/filtering run without decoding
    payloads (41455 tars <-> 41455 parquets, ~1.6MB vs ~270MB)
  - WebDataset key convention: files sharing a basename before the first dot form one logical
    sample; extension selects type (.jpg/.txt/.json)
  - incremental/resumable builds keyed on shard completion (incremental | overwrite | extend),
    retry up to max_shard_retry
  - multi-tier hash integrity: optional md5/sha256/sha512 per sample, verify_hash drops
    mismatches vs externally-supplied checksums
  - sequential-I/O-first tar packaging: 3-10x over random access, collapses millions of file
    handles to single digits
  - post-hoc small-file consolidation: pyspark compacts hundreds of thousands of parquet shards
    into ~32 large files
nest steals: Three concrete steals. (1) nest-format: formalize the "shadow columnar sidecar" inside the
             single .nest container. Today provenance + search_contract carry coarse metadata;
             add an optional additive section (reserved id 0x09+, never bump v1) holding a
             compact columnar SoA of per-chunk filterable scalars (source_id, lang, byte_len,
             token_count, dataset tag) so nest-cli stats/filtered-search and nest-runtime can
             pre-filter candidate chunks WITHOUT decoding chunks_canonical text or touching
             embeddings on the hot path -- a pure metadata scan, mirroring parquet-without-tar.
             The scalar columns are tiny, delta/zstd-friendly (zstd already allowed on
             non-embedding sections), and let search skip-list before SIMD scoring. (2)
             nest-format hashing/layout: adopt the 1:1 ordered-alignment invariant explicitly as
             a frozen guarantee -- chunk_ids[i], chunks_canonical[i], chunks_original_spans[i],
             embeddings[i] and any new scalar column[i] all share index i, so
             nest://content_hash/chunk_id resolves to one offset across every section; this is
             the on-disk analog of tar<->parquet<->npy alignment and strengthens the
             deterministic contract. (3) nest-cli: borrow the composite positional key idea for
             chunk_ids -- a deterministic sortable key (source-shard prefix + monotone index)
             makes builds reproducible and enables future incremental/extend rebuilds (append
             new chunks as a new logical shard range) without rewriting prior sections, aligning
             with the additive-only rule. The downloader/distributed/fsspec machinery is out of
             scope (nest is offline-by-construction, never opens a socket); only the on-disk
             layout discipline transfers.
compression: Medium-high but indirect. img2dataset is a downloader, not a codec, so it offers no entropy
             coder or quantization scheme to beat. The transferable compression lever is the
             shadow-sidecar layout: separating tiny filterable scalar columns from the heavy
             text/embedding payload lets nest (a) zstd-compress the scalar columns extremely
             well via columnar SoA + delta coding (homogeneous columns compress far better than
             row-interleaved metadata), and (b) prune candidates before scoring so less of the
             file is touched on the hot path. It reinforces nest's existing principle that
             embeddings stay raw/mmap-scored while everything else is squeezed.
perf:        Reference numbers: ~1350 images/s/machine (~116M/24h) via K=10000 shards, N=cpu-count processes,
             M threads each, one tar per process to avoid disk contention. Parquet sidecar in
             LAION-400M is ~1.6MB vs ~270MB tar (>150x smaller) -- the quantitative case for
             metadata-only scans. Sequential tar I/O is cited at 3-10x faster than random access
             on local drives. None of this involves SIMD or a custom codec; it is process/thread
             orchestration plus I/O layout. For nest the takeaway is purely architectural: keep
             the scored array contiguous and order-aligned, keep filterable metadata in a
             separate tiny columnar block.
