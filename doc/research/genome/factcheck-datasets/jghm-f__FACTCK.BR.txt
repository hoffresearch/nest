what:        A 1,309-row UTF-8 TSV corpus of Brazilian Portuguese fact-checks (9 columns) harvested from
             agency RSS feeds by parsing schema.org ClaimReview JSON-LD, where each claim
             carries a normalizable truthfulness rating (ratingValue / bestRating +
             human-readable alternativeName label).</one_liner>
             <parameter name="core_innovation">The schema.org ClaimReview/reviewRating data model as a
             portable, normalized "truth verdict": a claim is represented by claimReviewed
             (text), a numeric ratingValue on a per-agency scale with bestRating as the scale
             maximum, and an alternativeName string label (e.g. "falso", "verdadeiro"). Dividing
             ratingValue/bestRating yields a source-agnostic truthfulness score in [0,1] that
             lets you fuse incompatible agency label vocabularies into one comparable axis. The
             harvesting is itself a clean ETL: pull JSON-LD (application/ld+json) out of
             fact-check pages, map reviewRating fields directly to columns, drop exact-row
             duplicates with URL as implicit primary key.
innovation:  The schema.org ClaimReview/reviewRating data model as a portable normalized truth verdict,
             harvested from JSON-LD, where ratingValue/bestRating yields a source-agnostic
             truthfulness score in [0,1] that unifies incompatible per-agency label
             vocabularies.
techniques:
  - schema.org ClaimReview JSON-LD extraction from <script type=application/ld+json> tags via
    feedparser + BeautifulSoup findAll
  - reviewRating triple: ratingValue (numeric), bestRating (scale max), alternateName (text
    label) -> normalized truth score = ratingValue/bestRating in [0,1]
  - field-to-column direct mapping (url, author.url, datePublished, claimReviewed,
    reviewBody/description fallback, ratingValue, bestRating, alternateName, itemReviewed.@type)
  - text normalization: re_char() strips non-ASCII except PT accented chars, saxutils.unescape()
    for HTML entities
  - exact-row drop_duplicates() dedup with URL as primary key
  - UTF-8 TSV (tab-separated) flat-table on-disk format, 9 columns x 1309 rows
nest steals: This is a truth-feature / provenance pattern, not a compression codec, so it lands in
             nest-format provenance + the demo corpus pipeline rather than the codec layer. Two
             concrete adaptations: (1) Extend the provenance section schema in nest-format
             (crates/nest-format/src/sections, additive within v1 since provenance is already
             required) to carry an optional per-chunk verdict record {rating_value:u16 LE,
             best_rating:u16 LE, label_id:u8} mirroring reviewRating, with label strings
             interned in a small dictionary, so a chunk that is a fact-checked claim ships its
             normalized truthfulness alongside its content_hash citation. (2) In the python
             builder (nest-python / build pipeline that ships the PT-BR fake-news demo corpus),
             add a ClaimReview JSON-LD ingester that maps reviewRating -> the new provenance
             fields and computes ratingValue/bestRating as a deterministic normalized score.
             This directly enriches nest's existing demo domain (it already ships PT-BR
             fake-news datasets) and gives nest a real "truth feature":
             nest://content_hash/chunk_id citations can then return both the exact byte span AND
             its agency verdict, deterministically. Because labels are dictionary-interned u8
             ids and the verdict struct is tiny repr(C) LE integers, it also compresses well
             under the existing zstd path on non-embedding sections.
compression: Low for raw byte-compression: the dataset is a 1,309-row TSV with no entropy coder,
             quantization, or codec to steal. Its compression-adjacent value is schema
             compactness: representing a verdict as ratingValue/bestRating/label_id (a few LE
             integers + a dictionary id) instead of free-text labels is a small domain-specific
             dictionary-coding win, and storing labels as interned u8 ids rather than repeated
             UTF-8 strings reduces provenance-section size before zstd. So it is relevant only
             as a tiny structured-field encoding pattern for the provenance section, not as a
             general compression technique.
perf:        No performance characteristics of interest: pure-Python offline ETL (feedparser + BeautifulSoup
             + requests), no SIMD, no on-disk index, no large-scale data. The TSV is tiny
             (~1,309 rows). Only the score-normalization formula and the verdict-field layout
             transfer; nothing about throughput or memory is relevant to nest's hot path (and
             nothing here touches embeddings, which nest never compresses on the scoring path).
