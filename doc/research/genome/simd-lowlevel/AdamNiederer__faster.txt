what:        A Rust "SIMD for humans" library that exposes vectorized computation as iterator combinators
             (simd_iter / simd_map / simd_reduce / scalar_collect) over width-agnostic vector
             types (f32s, i8s, etc.), compiling each closure body down to 100% native SIMD via
             thin intrinsic wrappers plus scalar polyfills for missing instructions.
innovation:  see field
techniques:
  - Iterator combinators over SIMD: simd_iter/simd_map/simd_reduce/scalar_collect mirroring std
    iterators, so vectorized math reads like scalar math
  - Width-agnostic vector types (f32s, i8s, u8s): a single source kernel auto-selects f32x8
    (AVX2) / f32x4 (NEON) / scalar, sized to the largest register the target supports
  - Default-value tail padding: uneven collections are finished by padding the last partial
    vector with a user-supplied identity value (e.g. 0.0) so the full-width SIMD kernel runs
    end-to-end, eliminating the scalar remainder loop (benchmarks: uneven within ~1% of even)
  - Thin-wrapper + polyfill portability: each op is a 1-line wrapper around an intrinsic, with a
    scalar polyfill that only activates on targets lacking the instruction, so the same trait
    method compiles everywhere
  - Accumulator-vector reduction: simd_reduce keeps a full-width SIMD accumulator across the
    loop and does a single horizontal fold at the very end, not per-element
  - upcast/downcast lane-width conversions (e.g. i8 lanes widened to i32/f32 lanes) exposed as
    vector ops, matching mixed-precision dot products
  - Static dispatch with #[inline] + #[target_feature] so the hot loop has zero per-iteration
    CPUID/branch cost
nest steals: Apply to nest-runtime/src/simd/. (1) Steal the default-value tail-padding trick to kill the
             scalar tail loops in avx2.rs/neon.rs dot_f32_*/dot_f32_i8_* (currently lines 18-28
             and 52-55 are hand-written remainder loops): pad the embedding row's final partial
             vector with zeros (a safe FMA identity) so one masked/padded full-width FMA
             finishes the dim, shrinking each kernel and removing a per-query branch - directly
             helps since nest scores EVERY row off mmap on the hot path. (2) Adopt faster's
             thin-wrapper+polyfill discipline as the template for adding NEW quantized dtypes
             (int4/nf4/binary) to the search hot path without exploding the per-arch file count:
             define one dot_f32_qN trait with an avx2/neon wrapper plus a scalar polyfill,
             keeping files <=300 lines and the OnceLock dispatcher unchanged. (3) The
             upcast/downcast lane-widening pattern is exactly nest's i8->i32->f32 widening
             (avx2.rs lines 45-48) and is the blueprint for int4/binary kernels that unpack
             sub-byte lanes - the enabler for pushing the 'tiny' preset's 0.283 size ratio lower
             with binary/int4 embeddings while keeping a real-cosine rerank. Do NOT adopt
             faster's iterator API wholesale: it is compile-time-width-only and nest's OnceLock
             runtime dispatch is strictly better for shipping one portable binary.
compression: Indirect but real: faster's lane-widening (upcast/downcast) and polyfill discipline are the
             practical pattern for adding sub-byte quantized dot-product kernels (int4, nf4,
             binary/Hamming) to nest's hot path. Those new dtypes are what actually push the
             'tiny' preset below its current 0.283 size ratio, since embeddings (the bulk of
             bytes, never zstd-compressed because they are scored from mmap) can only shrink via
             lower-precision encodings that still vectorize. faster shows how to make each new
             precision a thin wrapper + scalar fallback rather than a new per-arch rewrite.
perf:        Hot-loop body compiles to 100% SIMD instructions ordered by LLVM; overhead vs hand-written
             intrinsics is within ~5% worst case, ~1% on the README example. Tail-padding makes
             uneven collections essentially free (reduce_uneven_simd 838ns vs reduce_simd 839ns;
             map_uneven 884ns vs map 879ns). Critical caveat for nest: dispatch is COMPILE-TIME
             only (no runtime feature selection - confirmed by the simdeez comparison), so a
             faster-built binary is pinned to the build host's widest ISA. nest's OnceLock
             function-pointer runtime dispatch already beats this for a single portable offline
             binary, so borrow the kernel/tail tricks, not the dispatch model. Performance can
             degrade only when a slow scalar polyfill is hit on an old CPU.
