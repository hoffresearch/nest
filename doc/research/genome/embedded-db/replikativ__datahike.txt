replikativ/datahike

siblings: ./00-index.txt   |   map: ../../README.txt

what:        A durable, immutable Datalog database that ports DataScript onto a content-addressed Hitchhiker
             tree (a fractal B+ tree with buffered write-logs) over the konserve pluggable KV
             store, giving append-only temporal facts, snapshot/time-travel, and
             structural-sharing dedup.
innovation:  Content-addressed persistent index nodes: every tree node is stored under an ID that is a
             cryptographic hash (hasch, SHA-512) of the node's own contents, so identical
             sub-structures across versions/snapshots automatically collapse to the same
             physical block (structural sharing + dedup for free), and a whole database version
             is named by a single root hash. This is the same idea nest already uses for
             content_hash, but pushed down to per-block granularity so that incremental edits
             only write the changed nodes while unchanged nodes are shared by reference.
techniques:
  - Hitchhiker (fractal) tree: B+ tree whose internal index nodes carry a bounded append-log of
    pending insert/retract ops, flushed downward in batches only when the buffer overflows,
    amortizing write amplification across many mutations
  - Content-addressed nodes: node UUID = hash(node contents) via hasch SHA-512, yielding
    deterministic IDs, automatic dedup, and verifiable integrity (analogous to nest per-section
    SHA-256)
  - Datom = [entity, attribute, value, tx] fact tuples stored in three sorted covering indexes
    EAVT / AEVT / AVET, giving column-store-like locality without a separate columnar layout
  - Append-only fact log: retractions are new datoms with an assertion flag, so history is never
    overwritten; time-travel (as-of / history) is a filter over tx ids, with snapshots sharing
    structure
  - Block granularity in KV: leaf data nodes hold a sorted vector of many datoms (a block), not
    one-datom-per-key, cutting KV overhead and improving scan locality
  - konserve KV abstraction decoupling logical index from physical store (File/LMDB/S3/JDBC),
    with only the root-id map mutated in place
  - GDPR 'excision': because facts are addressable, specific historical values can be purged
    while keeping the rest of the immutable log intact
nest steals: Two concrete steals into nest-format and nest-runtime. (1) In nest-format hashing.rs: extend
             nest's content_hash model to PER-BLOCK content-addressed chunk nodes so that when
             nest gains real-time edit, an edit rewrites only the touched blocks and shares
             unchanged ones by their SHA-256 id inside the single .nest file -- this is exactly
             the structural-sharing dedup that lets a v2 'append region' grow without rewriting
             the whole file, while keeping byte-determinism. (2) In nest-runtime, model
             edits/retractions as an append-only fact log (a reserved section 0x09+, additive
             within v1) carrying [chunk_id, op, tx] tuples plus a small fractal-style
             buffered-flush index, so temporal 'as-of' queries and undo become a filter over tx
             ids without mutating frozen sections -- gives nest the 'real-time edit' and
             'temporal' pillars of the north star while preserving the
             frozen-format/offline/deterministic guarantees. The EAVT/AEVT/AVET
             sorted-covering-index trick informs how to lay out a future graph-search section
             (chunk-relations) as sorted tuple blocks scored directly off mmap.
compression: Medium-high for compression specifically: the per-block content-addressed structural sharing IS
             a compression mechanism -- duplicate chunks/embeddings/index-nodes across versions
             or across similar corpora deduplicate to a single physical block, so a
             multi-version or multi-corpus .nest pays once. This directly serves 'compress more
             than everyone' when nest stores whole evolving databases/repos with overlapping
             content, and the fractal write-buffer keeps that dedup cheap under real-time edit
             instead of forcing full re-encode.
perf:        Hitchhiker tree trades a small read cost (must merge a node's pending log on read) for large
             write-amplification savings: O(buffered) flushes instead of per-insert rebalances,
             ideal for high-ingest append workloads. Block-granular leaves give sequential scan
             locality similar to a column store. Content-addressing makes reads cache-friendly
             and integrity-checkable but adds a hash computation per node write (SHA-512 there;
             nest would reuse its existing SHA-256 surfaces, no new dependency). All structures
             are persistent/immutable so reads are lock-free -- aligns with nest's mmap read
             path.
