what:        XTDB v2 is a bitemporal SQL database whose primary index is a distributed LSM tree of immutable
             Apache Arrow files, sharded by a 2-bit (branching-factor-4) HAMT trie over
             entity-id, where each file publishes min/max + bloom-filter metadata and a single
             collapsed "recency" scalar so the query engine can prune whole files before
             touching their columnar buffers.
innovation:  Collapse a multi-dimensional temporal coordinate (valid_time, system_time) into ONE monotone
             sortable scalar ("recency" = max T at which the row was believed valid for both
             valid-time=T and system-time=T), publish it as per-file metadata alongside min/max
             ranges and bloom filters, then prune entire immutable files at query time without
             decoding their payload. This is a generic "skip-index on a derived sort key + cheap
             per-file summary statistics" pattern, decoupled from temporality.
techniques:
  - 2-bit HAMT trie (branching factor 4) over entity-id hash; trie path [3,2,1,0] = recursive
    prefix buckets that double as deterministic file shard names (210/211/212/213) and keep
    ~100MB files
  - LSM tree of append-only immutable files; compaction merge-sorts L0->L1->L2 and CONCATENATES
    bitemporal events instead of dropping versions; a file is 'superseded' only when its
    compacted output commits, making cache invalidation trivial
  - Per-file zone-map metadata: min/max for numeric columns + Bloom filters for non-numeric
    columns, used for predicate pushdown / file skipping before reading Arrow buffers
  - Recency heuristic: collapse (valid_time, system_time) into one sortable scalar so 'give me
    data newer than T' elides whole historical files
  - Survivor vs historical split at L1: current versions sharded by entity-id only; superseded
    versions sharded by entity-id AND recency, so hot current-state scans never touch cold
    history
  - Apache Arrow columnar layout chosen because remote/immutable storage already forbids
    in-place update, so columnar scan locality comes for free
  - Deferred leaf sorting: HAMT leaf stays unsorted until it exceeds 1024 bytes and is promoted
    to a branch, amortizing sort cost
nest steals: Two steals, both anchored in nest-format. (1) ZONE-MAP/SUMMARY metadata per section, additively:
             extend the manifest entry in crates/nest-format/src/manifest and the section
             descriptors in crates/nest-format/src/sections so each section (chunks_canonical,
             provenance, future edit-log) carries cheap precomputed summaries -- for embeddings,
             per-block min/max per dimension or a coarse centroid; for text/provenance, a
             deterministic Bloom filter over tokens/source-ids. Then
             crates/nest-runtime/src/search.rs and bm25 skip blocks whose Bloom filter cannot
             contain a query term and whose summary cannot beat the current top-k cosine bound,
             cutting SIMD dot products and mmap page faults without changing scored bytes (exact
             cosine rerank stays ground truth). Implement as a new RESERVED optional section
             'section_zonemaps(0x09)' or new optional manifest fields -- additive, never a v2
             bump. (2) RECENCY-SCALAR for nest's future real-time edit dimension: model each
             chunk version's (valid_from, ingested_at) as one monotone u64 'recency' stored in
             chunk_ids or a new edit-index section, kept sorted so 'serve current state' and
             'as-of T' queries prune superseded chunk versions deterministically; the LSM
             survivor/historical split gives a coordination-free, single-file, append-only edit
             model that stays deterministic (seeded, alphabetical term order) and offline by
             construction.
compression: Indirect but real. The zone-map/Bloom skip-index does not shrink the file but lets nest keep
             MORE data in one .nest container while staying fast, because cold blocks are never
             paged in or decoded -- it makes large-corpus single-file serving viable, the
             scaling axis of the 'compress AND serve whole databases' north star. The
             recency-collapse + LSM-concat compaction is the canonical compact way to store full
             edit history: one append-only sorted run that compacts and dedups instead of N
             snapshots, so historical versions migrate to deeper denser blocks that zstd (nest's
             existing non-embedding codec) compresses well. Bloom filters are themselves a
             compact (~10 bits/elem) probabilistic substitute for an exact term dictionary.
perf:        Index lives on object storage and is cached across nodes (irrelevant to nest's single-file
             offline model -- adapt the file-skip idea, drop the distribution). Pruning works
             because Arrow buffers are columnar and contiguous, so a passed zone-map check
             yields a tight sequential scan; nest's mmap + SIMD dot-product hot path benefits
             identically -- skipping a block avoids both page faults and AVX2/NEON work. The
             ~100MB shard size and 1024-byte leaf-promotion threshold are tuning knobs worth
             mirroring as nest block sizes. Bloom false positives cost one wasted block scan,
             never a wrong answer; nest's mandatory exact rerank preserves correctness
             regardless.
