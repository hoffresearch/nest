what:        Knowhere is the C++ vector-search core of Milvus, a unified index/config factory wrapping a
             Zilliz-optimized FAISS fork plus hnswlib and DiskANN, exposing
             HNSW/IVF/DiskANN/IVF_RABITQ indexes with SQ1-SQ8, PQ, and 1-bit RaBitQ quantization
             over a templated fp32/fp16/bf16/int8/bin1 operand type system with AVX512-VPOPCNTDQ
             and ARM-SVE SIMD kernels.
innovation:  RaBitQ 1-bit quantization: random-orthogonal-rotate a centroid-normalized vector, take the sign
             of each dimension to get a D-bit code (1 bit/dim, no codebook), store 2 small
             per-vector float scalars, and recover a provably-unbiased cosine/distance estimate
             with O(1/sqrt(D)) error bound using only bitwise-AND + popcount against a
             4-bit-decomposed query, then exact-rerank a refine_k-larger candidate pool with
             higher precision. This is the textbook recipe for "compress harder than int8 yet
             still return real cosine after rerank" that nest already half-implements.
techniques:
  - RaBitQ: random orthogonal rotation + sign() = 1-bit-per-dim code, no stored codebook
    (1536-dim vector -> 192 bytes)
  - Two precomputed per-vector float scalars give an unbiased distance estimator with
    O(1/sqrt(D)) error bound
  - Asymmetric distance: data 1-bit, query in Bq=4 bit-planes; estimate =
    1*popcount(code&q1)+2*popcount(code&q2)+4*popcount(code&q3)+8*popcount(code&q4)
  - AVX512 VPOPCNTDQ and ARM SVE popcount kernels for the bitwise hot path; ~3x faster than PQ
    LUT lookups
  - Incremental refinement: split code into MSB binary-code + ex-code, coarse estimate first
    then refine bits on demand
  - DiskANN dynamic PQ+Refine: doubles K each round to emulate range search, switches to
    PQ+Refine when >x% of bits set
  - centroid-relative normalization (global or per-cluster centroid) to improve local 1-bit
    encoding accuracy
  - templated operand type system (fp32/fp16/bf16/int8/bin1/sparse) with compile-time
    feature-flag typeCheck and MockData->fp32 promotion
nest steals: Add a RaBitQ-style 1-bit codec as a new encoding id in nest-format (encoding ids 4-255 are
             RESERVED in v1, so this is additive and does NOT bump NEST_FORMAT_VERSION): apply
             it ONLY to the embeddings section, storing a deterministic seeded random rotation
             (or a fixed Hadamard/structured rotate to avoid storing a dense matrix), the packed
             D-bit sign codes, plus 2 little-endian f32 scalars per vector in a repr(C) struct.
             This becomes a new preset below "tiny" -- call it "atom" -- pushing the 0.283 size
             ratio toward ~0.05-0.08 for the embedding bytes (1 bit/dim vs int8's 8 bit/dim). In
             nest-runtime, the simd dispatcher (currently AVX2/NEON/scalar dot) gains a
             bitwise-AND+popcount path (AVX2 has no native VPOPCNTDQ, so use the SSSE3/AVX2
             nibble-LUT popcount or vcntq_u8 on NEON) to produce the 1-bit estimate cheaply,
             then -- critically -- nest's MANDATORY exact-cosine rerank stays exactly as is: the
             1-bit codes are pure candidate generation, the returned score is still real cosine
             read from a small materialized f32/f16 refine set, preserving the search_contract
             guarantee that score is never an ann proxy. Keep determinism by seeding the
             rotation and using alphabetical/stable tie-breaks. Each nest-runtime file stays
             <=300 lines by isolating the codec (rabitq_codec.rs) from the popcount kernel
             (simd/popcount.rs).
compression: Directly central to the north star of "compress data more than everyone." RaBitQ is the single
             most compact published vector encoding that still supports search: 1 bit/dimension
             with NO codebook and a proven error bound, an 8x shrink over nest's current int8
             embedding mode and ~32x over f32. Because nest already mandates an exact-cosine
             rerank, it gets RaBitQ's recall recovery essentially for free -- the risky part of
             1-bit quantization (lossy scores) is already neutralized by nest's architecture.
             This is the highest-leverage compression idea available for the embeddings section.
perf:        Bitwise-AND+popcount distance is ~3x faster than PQ LUT-in-RAM scans and runs near 1 cycle/word
             on VPOPCNTDQ hardware. On nest's targets: x86_64 AVX2 lacks VPOPCNTDQ so use the
             Mula nibble-shuffle popcount (pshufb LUT) for ~16-32 bytes/iter; aarch64 NEON uses
             vcntq_u8 + horizontal add, which is excellent. The 1-bit codes are tiny and
             mmap-friendly (192 bytes for a 1536-d vector), so far more candidates fit in cache,
             improving candidate generation before rerank. Asymmetric 4-bit query keeps full
             query info while data stays 1-bit. Memory: 2 extra f32/vector overhead (8 bytes) is
             negligible vs the bit savings.
