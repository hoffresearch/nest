what:        A Rust-core tokenization library (Python/Node/Ruby bindings) implementing BPE, WordPiece,
             Unigram and WordLevel behind a five-stage normalizer -> pre-tokenizer -> model ->
             post-processor -> decoder pipeline, with full original-span alignment tracking and
             a single self-describing tokenizer.json serialization.
innovation:  Reversible byte-level alphabet (GPT-2 scheme): the 256 raw bytes are bijectively remapped to
             printable Unicode codepoints so any byte stream - CJK, Thai, emoji, binary, JSON,
             PDF text - is losslessly tokenizable by a learned subword vocabulary with zero UNK
             and zero out-of-vocab loss, turning a learned merge table into a reversible
             variable-length dictionary code over arbitrary bytes.
techniques:
  - Byte-level BPE: bijective 256-byte to printable-Unicode map (byte_level.rs) so the model
    alphabet is closed and tokenization is fully reversible/lossless on any input
  - BPE merge_word: Word as Vec of (symbol, prev, next) linked-array plus a BinaryHeap of Merge
    candidates keyed by (rank, pos); merges lowest-rank pair first with deterministic tie-break
    (leftmost), O(n log n) per word
  - merges stored as HashMap<(u32,u32), (rank:u32, new_id:u32)> - pair-rank lookup, not string
    compares; vocab as HashMap<String,u32> plus reverse Vec for id_to_token
  - Unigram model: Viterbi forward-DP over a lattice of all substrings present in vocab, scored
    by log-probabilities, returns minimum-cost (most-probable) segmentation; trained via EM with
    iterative pruning
  - LRU word-result cache (cache.rs) + per-thread cache (PR 2028) to memoize BPE output per
    pre-token, +47-62% on parallel workloads
  - byte_fallback (SentencePiece trick): unknown chars decomposed to <0xNN> byte tokens so vocab
    stays small but coverage is total
  - Full alignment/offset tracking: every token carries (start,end) byte offsets back into the
    ORIGINAL string even through destructive (NFKC/lowercase/strip) normalization
  - Single self-describing tokenizer.json via serde: one file carries
    normalizer+pre_tokenizer+model(vocab,merges)+post_processor+decoder, version-tagged,
    reconstructs the exact pipeline
nest steals: Three concrete lifts. (1) Replace the word-segmented bm25 tokenizer in nest-runtime/src/bm25
             with a byte-level pre-tokenizer + tiny deterministic BPE/Unigram model: kills the
             known CJK/Thai degradation gap, stays deterministic (alphabetical-equivalent
             merge-rank order), needs no extra section. (2) Add a learned-BPE codec for the
             text-bearing sections: train a per-file BPE/Unigram vocab over chunks_canonical,
             store the merge table as a new RESERVED encoding id (4-255) in
             nest-format/src/encoding, and emit token-id streams instead of raw UTF-8 - this is
             dictionary compression that composes with zstd and is the single most
             mission-relevant idea for compress-more-than-everyone on repetitive corpora;
             vocab+merges become a deterministic part of content_hash. (3) Steal the
             offset-alignment model to harden chunks_original_spans: nest already maps
             canonical->original; the (start,end)-through-normalization technique is the proven
             design for keeping nest://content_hash/chunk_id byte-exact after lossy
             normalization. Mirror the single tokenizer.json idea: keep the tokenizer config
             inline in the manifest so the file stays self-describing and offline.
compression: Directly central: a learned BPE/Unigram vocabulary IS a variable-length dictionary code, and the
             byte-level alphabet makes it lossless and reversible on arbitrary bytes
             (text/json/yaml/pdf-text). Token-id streams shrink repetitive corpora before zstd,
             and Unigram-Viterbi gives provably minimum-cost segmentation. The merge table is
             the entropy-model that beats generic zstd on structured/repetitive data - the core
             lever for the compress-more-than-everyone north star. Caveat: must never be applied
             to the embeddings section (hot-path SIMD scoring needs raw f32/f16/int8 off mmap),
             only to text-bearing sections.
perf:        Rust core tokenizes ~1GB/CPU-min (<20s/GB cited). Hot path is merge_word with the BinaryHeap;
             LRU + per-thread cache memoize per pre-token (single-thread flat, +47-62% at 88+
             threads). Merge lookups are integer (u32,u32) HashMap probes, no string compares.
             Build-time win: BPE::Builder no longer formats strings in hot loop (~45% faster
             from_file on Llama-3). No SIMD in the tokenizer itself; parallelism is rayon over
             the batch. Memory: vocab+merges are plain HashMaps, fits easily; tokenizer.json for
             large LLM vocabs (128k-256k) is a few MB.
