what:        A distributed graph database that maps an adjacency-list graph onto any BigTable-model store
             (Cassandra/HBase/Bigtable), serializing each incident edge as one sorted cell whose
             bytes are sort-key-ordered and shrunk with variable-length integer encoding plus
             delta-encoded neighbor ids.
innovation:  The edge-as-cell encoding: each edge is one byte string laid out so that lexicographic byte
             order equals the logical sort order (label id with direction bit stolen into the
             low bit, then sort-key property bytes, then neighbor id, then edge id), and the
             neighbor vertex id is stored as a signed DELTA against the row-owner vertex id
             rather than its absolute 64-bit value. Combined with locality-aware id assignment
             (co-accessed vertices get numerically close ids), the deltas stay small and the
             whole edge collapses to a few varint bytes. Compression AND traversal-order
             indexing fall out of the SAME byte layout, with no separate index structure.
techniques:
  - Adjacency-list-as-row: vertex = row keyed by 64-bit id, each edge/property = one sorted
    cell, enabling range-scan retrieval of edge subsets
  - Variable-length integer (varint) encoding of label ids, sort keys, neighbor ids, edge ids so
    small numbers cost 1-2 bytes
  - Delta encoding of the adjacent vertex id relative to the owning row's vertex id (store
    difference, not absolute)
  - Direction bit packed into the low bit of the label id (bit-stealing) instead of a separate
    byte
  - Order-preserving serialization: column bytes arranged so lexicographic order == edge-label
    sort order, making the sort the index (vertex-centric indices are column-range scans)
  - Locality-aware id allocation: ids assigned so co-accessed entities have small absolute id
    difference, partitioning data and minimizing deltas
  - Column/value split: structural+sort bytes in the sorted column, signature property values
    get compressed serialization in the value, ad-hoc properties uncompressed in the value
nest steals: Two targeted lifts, both in nest-format (crates/nest-format/src/sections + encoding). (1) Add a
             graph-search section (reserved id 0x09+, additive within v1) when nest grows graph
             search: encode each node's adjacency list as a sorted run of (varint label,
             delta-to-owner neighbor index, varint edge-id) triples with the direction bit
             stolen into the label low bit. chunk_ids are already a dense 0..N index space, so
             delta-to-owner makes neighbor refs 1-2 bytes; a new codec, not a format break. (2)
             Useful even without graph search: apply varint+delta to the existing
             chunks_original_spans section (offset/length pairs are monotonic, locally small)
             and to chunk_ids, as a new encoding id (4-255 reserved) selectable per-section in
             the manifest, scored off mmap with zero-copy varint decode in nest-runtime.
             Order-preserving bytes also reinforce nest's deterministic build: a canonical sort
             + delta layout is inherently reproducible and content-hash-stable.
compression: High for non-embedding sections. Delta+varint is the classic way to compress
             monotonic/locally-clustered integer streams (spans, ids, future adjacency) and
             stacks under zstd for further gains, advancing 'compress more than everyone'. It
             does NOT touch embeddings (kept raw for SIMD hot-path scoring per nest's contract),
             so it complements the tiny/compressed presets rather than conflicting. The
             delta-to-owner trick specifically unlocks compact graph-search payloads later.
perf:        Varint decode is branchy but cache-friendly and zero-copy off mmap; delta decode is a single
             running-sum (prefix-sum) pass, trivially fast and SIMD-able for bulk neighbor-id
             reconstruction (NEON/AVX2 prefix sum). Order-preserving layout means
             traversal/range queries are memcmp-ordered scans, no separate index load. Main cost
             is encode-time sorting and id assignment, a build-time (python) concern, not
             runtime.
