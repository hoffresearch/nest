what:        A property-graph database built on Redis modules that represents every relationship type as a
             GraphBLAS sparse adjacency matrix and executes openCypher traversals as sparse
             linear algebra (matrix multiply / masked semirings) rather than pointer-chasing
             adjacency lists.
innovation:  Model a graph as a set of sparse boolean adjacency matrices and let an adaptive storage layer
             (SuiteSparse:GraphBLAS) pick the most compact of four formats per matrix at runtime
             -- hypersparse (DCSC) / sparse (CSC) / bitmap / full -- plus an "iso" mode that
             stores a single scalar instead of a value array when all stored entries are
             identical (e.g. unweighted edges = all-true). Adjacency is thus compressed by
             structure (sparsity-tier selection) AND by value (iso de-duplication), and the
             entire k-hop traversal collapses to A^k matrix products, so the relationship
             topology is both the index and the query plan.
techniques:
  - Adaptive 4-tier sparse format auto-selection per matrix: hypersparse DCSC (only nonempty
    columns get a pointer), sparse CSC, bitmap (1 bit/cell), full -- chosen by density so
    storage tracks actual occupancy
  - Iso / uniform-valued matrices: when every stored value is identical, store ONE scalar
    instead of an N-length value array (ideal for boolean adjacency / unweighted graphs)
  - Doubly-compressed sparse column (DCSC/hypersparse): a second index level over column
    pointers so empty columns cost zero, scaling to billions of dimensions with few nonzeros
  - Delta-Matrix write buffering: M (committed) + delta-plus (pending adds) + delta-minus
    (pending deletes); reads merge the three, writes batch until DELTA_MAX_PENDING_CHANGES then
    a single GrB_wait flush, avoiding per-write resort
  - Traversal-as-linear-algebra: friends-of-friends = F^2, pattern (A)->(B)->(C)<-(A) =
    A*B*transpose(A); masked matrix-multiply with semirings prunes the result during the
    multiply
  - One matrix per relation type + one type-agnostic adjacency matrix + symmetric diagonal label
    matrices, so labels/edge-types are selected by matrix choice not by per-row filtering
  - Transpose matrices maintained alongside forward matrices so reverse traversal is also a
    multiply, never a scan
nest steals: Add an optional graph/relations section to nest-format (reserved section id 0x09+, additive
             within v1) that stores adjacency as a DCSC/hypersparse triple (column-pointer
             array, row-index array, optional iso-scalar value) with all integers little-endian
             unsigned per the repr(C) rule -- this lets a .nest container carry the edge
             structure of a corpus (citation links, chunk-to-chunk references, knowledge-graph
             edges) at near-zero extra bytes when iso/boolean. The biggest steal is the
             FORMAT-SELECTION HEURISTIC for nest-format's encoding layer: today encodings
             (raw/zstd/f16/int8) are chosen per-preset, but FalkorDB's per-matrix density-tiered
             pick (bitmap when dense, hypersparse when ultra-sparse, iso when constant) is
             exactly the discipline nest needs to choose the smallest codec PER SECTION based on
             measured statistics, deterministically. In nest-runtime, a small CSC/DCSC reader
             behind the existing mmap+SIMD dispatcher enables graph-search (1-2 hop neighbor
             expansion as sparse mat-vec straight off mmap, scalar-portable, no GraphBLAS
             dependency) which is a named north-star gap. The delta-plus/delta-minus buffer
             pattern is the clean blueprint for nest's planned real-time edit: keep the frozen
             mmap'd section immutable and merge a tiny pending-add/pending-delete overlay at
             read time, flushing to a new deterministic container on commit -- preserving the
             single-file/deterministic guarantees.
compression: High and direct. Iso (single-scalar) storage plus density-tiered sparse formats is a textbook
             way to compress structured/relational data far below generic zstd: a boolean
             adjacency with N nonzeros costs ~N row-indices + column pointers and ONE value
             byte, versus a dense or text edge list. This is precisely the 'compress whole
             databases/repos and graphs' part of nest's north star, and the per-section
             format-selection heuristic raises the compression ceiling for every section, not
             just graphs.
perf:        GraphBLAS uses OpenMP-parallel saxpy-vs-dot meta-algorithm for masked matmul and exploits AVX
             where available; the 256-variant masked C<M>=A*B kernel dispatch is overkill for
             nest. For nest, the relevant takeaway is the access pattern, not the parallelism:
             DCSC/CSC are pure flat arrays (col-ptr, row-idx, vals) that mmap and scan linearly,
             so a sparse mat-vec for k-hop neighbor expansion is cache-friendly and
             SIMD-amenable with nest's existing scalar/AVX2/NEON dispatcher -- no need to vendor
             SuiteSparse (heavyweight C, would blow the small-core and offline constraints). Iso
             matrices also make integrity hashing cheaper since the value array is a single
             scalar.
