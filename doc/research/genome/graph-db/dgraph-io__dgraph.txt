dgraph-io/dgraph (with companion repos dgraph-io/sroar and dgraph-io/badger)
category: graph-db   |   steal priority: HIGH
================================================================================================

siblings: ./00-index.txt   |   map: ../../README.txt

what:        A distributed GraphQL/DQL graph database storing each predicate as a sorted posting list of
             64-bit node UIDs, encoded as serialized roaring bitmaps (sroar) whose in-memory
             byte layout equals the on-disk layout, persisted in a WiscKey-style LSM+value-log
             KV store (Badger).
innovation:  sroar: a serialized roaring bitmap whose in-memory representation equals its on-disk
             representation (single []uint16 buffer), so an integer-id set / graph adjacency
             list is mmapped and set-operated with zero marshal/unmarshal -- compressed storage
             that is also directly operable, matching nest's no-decode-on-hot-path rule.
techniques:
  - Serialized roaring bitmap (sroar): single []uint16 buffer, zero-copy mmap, no
    marshal/unmarshal; keys section (header of node-size + key-count, then 48-bit-base-key ->
    container-offset pairs) followed by sequential containers
  - Two container types selected by density: array container (sorted uint16 list) below 4096
    cardinality, bitmap container (1024 uint64 = 8KB dense bitset) above it; run containers
    deliberately omitted to keep impl simple yet faster
  - 64-bit keyspace split: mask 0xFFFFFFFF0000 isolates the high 48 bits as the container base
    key, low 16 bits are the index within a container (uint16)
  - Per-container header words: [size, type, cardinality] then payload, so And/Or/AndNot iterate
    matching base keys and run containerAnd/containerOr directly on slices via pointer/reslice
    arithmetic (FastAnd/FastOr pre-size the destination from cardinality estimates)
  - Group-varint delta encoding (the predecessor scheme): split sorted id list into fixed
    128-int blocks, store first value whole then deltas as varints (frame-of-reference); cheap
    but requires decode -> superseded by sroar
  - Posting list as graph primitive: predicate:entity -> sorted list of value-ids, so a graph
    join becomes a sorted-set intersection (bitmap AND) instead of an application-layer hash
    join
  - WiscKey key-value separation (Badger): small keys stay in the LSM tree, large values go to
    an append-only value log, cutting write amplification; SSTable blocks compressed with Snappy
    or Zstandard, bloom filters + block cache for reads
  - Mutations as WAL + in-memory overlay layers over an immutable base posting list (separate
    layers for replace vs add/delete) to avoid re-sorting the whole list on every write
nest steals: Two concrete steals. (1) Add a serialized-roaring-bitmap codec to nest-format (new RESERVED
             encoding id, e.g. 0x04, or a helper in encoding/) for any section that is a SORTED
             SET OF u32/u64 ids: chunk_ids, hnsw neighbor adjacency lists, and bm25 postings
             (term -> doc-id list in 0x08). Mirror sroar's contract exactly: the encoded bytes
             ARE the in-memory layout, so nest-runtime mmaps and runs set intersections (AND)
             with no decode, matching nest's "no decode on hot path" rule. Store containers
             little-endian repr(C) per nest constraints; determinism is free because roaring
             container choice is a pure function of the id set (array<4096 cardinality else
             dense bitmap). This unlocks (a) a graph_index section (0x09+) where each node's
             adjacency = a roaring bitmap, giving the "graph search" north-star item with
             compressed, mmap-scored traversal; and (b) much smaller bm25 postings than raw
             varint id lists, improving the tiny/hybrid presets' size ratio. (2) Adopt the
             array-vs-bitmap density switch as a general nest codec primitive in
             nest-format/encoding for sorted-id sections, and reuse the group-varint
             frame-of-reference (first value + 128-block deltas) as the int8-tier analog for
             monotonic id columns like chunks_original_spans offsets, shrinking provenance/span
             sections in compressed/tiny presets. Skip Badger/LSM entirely: it is a mutable
             multi-file server store and violates nest's single-file/offline/append-only
             invariants -- only the sroar byte-layout discipline and the
             posting-list=set-intersection model transfer.
compression: Directly on-mission. Roaring bitmaps are the state-of-the-art compressed representation for
             sorted integer-id sets, and sroar proves you can get that compression while keeping
             a zero-copy mmap layout (no decode tax), which is exactly nest's hot-path
             constraint. For nest this shrinks bm25 postings, enables a compact compressed graph
             adjacency section, and gives a reusable sorted-id codec -- advancing "compress data
             more than everyone" for the non-embedding sections without ever touching the
             directly-scored embedding bytes.
perf:        sroar benchmarks: ~15x less memory, ~25x fewer allocations, ~7x faster than the reference Go
             roaring library, largely because there is no encode/decode step. Integrated into
             Dgraph v21.12 (Zion) with posting-list cache off, >40% of a heavy production
             workload's queries became >=20x faster and >50% became >=10x faster. Array
             containers cap at 4096 cardinality before switching to an 8KB dense bitmap (1024
             uint64); set operations are sorted-key merges over containers, so AND/OR are linear
             in container count and SIMD-friendly on the dense-bitmap path. Badger uses
             Snappy/Zstandard block compression plus bloom filters and a block cache; WiscKey
             separation trades read locality for far lower write amplification (not relevant to
             nest's read-only file).
