what:        ArangoDB is a multi-model (document + graph + search) database whose on-disk currency is
             VelocyPack (VPack): a single-type-byte, self-describing binary format with trailing
             offset-index tables that allow zero-copy O(1)/O(log n) random access into
             sub-documents without parsing the whole value, layered on a RocksDB LSM store.
innovation:  The trailing-offset-table layout enabling zero-copy random access into compactly-encoded
             structured values, with per-value smallest-width offset selection and an optional
             integer-key dictionary.
techniques:
  - Single-type-byte self-description: one leading byte encodes both type and size class
    (0x40-0xbe inline short strings up to 126 bytes, 0x30-0x39 single-byte small ints 0-9,
    0x20-0x27 width-tagged signed ints) so type+length read off the first byte(s)
  - Trailing index/offset table for O(1) array / O(log n) sorted-object random access without
    full parse
  - Smallest-width offset selection: pick 1/2/4/8-byte offsets based on max offset (<256, <64K,
    <4G, else) -- pay only for the addressing range actually needed
  - Compact types 0x13 (array) / 0x14 (object): drop the index table entirely and use
    LEB128-style varints (high bit = continuation) for bytelength + count, with the item count
    written backwards from the end for sequential-only/dump use cases
  - Object-key dictionary compression: two-pass collect+count of attribute names, replace
    repeated long keys with small integers via an O(1) hash table (e.g. 153KB->49KB,
    20.8KB->9.2KB in their benches)
  - Sorted-by-bytewise-key object storage enabling binary search and deterministic byte layout
  - Contiguous single-block memory layout (zero-copy) -- sub-value pointers are just base+offset
nest steals: nest currently stores chunks_canonical(text) and a future json/yaml/parquet payload as opaque
             encoded blobs. Adapt VPack's trailing-offset-table layout as a new additive section
             codec in nest-format (sections.rs + encoding.rs) for structured payloads: a
             json/yaml document section laid out as [tag][smallest-width offsets][values] so
             nest-runtime can mmap it and resolve a sub-path (e.g. doc.field[3].name) with pure
             base+offset arithmetic and binary search, zero decode, matching the same hot-path
             discipline already used for SIMD dot products straight off mmap. Two pieces are
             immediately stealable under nest's constraints: (1) the smallest-width offset
             selection (1/2/4/8 LE bytes) is a clean, deterministic, repr(C)-friendly encoding
             that fits the additive encoding-id space (ids 4-255 reserved in v1) and gives
             compact structured storage; (2) the object-key dictionary -- collect+count keys,
             emit a per-file key dictionary, replace keys with varints -- maps directly onto
             nest's content_hash determinism (sort keys bytewise => byte-identical output for
             identical input) and would massively shrink repeated-schema corpora like the PT-BR
             datasets and any parquet/jsonl ingest. The compact 0x13/0x14 varint mode is the
             right default for sequential/citation materialize paths where random access is not
             needed, squeezing the size ratio further toward the 'compress more than everyone'
             north star. All of this is offline, single-file, deterministic, and additive -- no
             v2 bump required.
compression: Directly central. VPack's key-dictionary + smallest-width offsets is a proven recipe for
             compressing structured/repeated-schema data (json, yaml, parquet rows, datasets)
             while STILL serving random sub-document access from raw mmap -- exactly nest's twin
             goals of extreme compression AND fast serve. It gives nest a principled structured
             codec that beats naive zstd-of-json on access cost (no decompress to read one
             field) and complements zstd: store the VPack-encoded structured payload, optionally
             zstd the non-hot parts. The standalone size wins are modest vs JSON (5-20%) but the
             key-dictionary path shows 2-3x reductions on repeated-schema data, and the
             zero-parse access is the real unlock for serving compressed
             datasets/whole-databases.
perf:        VPack is designed for in-kernel sub-document access used by indexes: type+length read from the
             first byte(s), values in one contiguous block, O(1) hash-table key->int
             translation. No SIMD in the format itself (it is a layout, not a kernel) -- it
             pairs well with nest's existing SIMD by keeping decoded fields byte-aligned and
             addressable. Index-table reads are random memory jumps; the compact 0x13/0x14 modes
             trade that random access for sequential scan to save the table bytes. Size benches:
             JSON->VPack typically 5-20% smaller; with key compression 153KB->49KB (~3.1x) and
             20.8KB->9.2KB (~2.3x). Caveat: object-key dictionary needs a second pass over input
             (acceptable in nest's python build stage, not the rust serve path).
