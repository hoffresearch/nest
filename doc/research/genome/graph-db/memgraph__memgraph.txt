what:        In-memory C++ property-graph engine using lock-free concurrent skip lists for vertices/edges,
             delta-chain MVCC (Hekaton-style snapshot isolation), full-snapshot + WAL durability
             with a section-offset binary file format, and a USearch/HNSW vector index using a
             single-store reference pattern.
innovation:  The PropertyStore "single-store reference + variable-length packed-metadata-byte" encoding: each
             property is prefixed by one metadata byte that bit-packs the value type tag, the
             byte-width of the property-key ID, and the byte-width-indicator of the payload, so
             integers/strings consume the smallest of 1/2/4/8 bytes and large values (like
             embedding vectors) are never duplicated in the row store but replaced by a small
             index-ID reference. A self-describing, additive, per-record variable-width codec
             that gives size wins without a separate schema and without a global dictionary
             pass.
techniques:
  - Packed metadata byte: bit-fields for {type tag, property-ID width,
    payload-size-width-indicator} in 1 byte before each value
  - Variable-length integer storage: ints in the minimum of 1/2/4/8 bytes that hold the value
    (LEB128-like family)
  - Name-to-ID mapper: intern property keys/labels to small integer IDs once, store IDs not
    strings per record
  - Single-store reference pattern: store a fat value (vector) only in its index backend;
    property store keeps just a u32/u64 index-ID reference
  - Snapshot/WAL layout: magic+version header, a section-offset table, then encoded-edges /
    encoded-vertices / indices / name-mapper / metadata / batch-info sections for seek-and-parse
    recovery
  - Batched + parallel snapshot writer/reader recorded in a batch-info section so write and
    recovery parallelize
  - Delta-chain MVCC: per-object delta linked list, visibility resolved at read time by
    transaction timestamp (snapshot isolation)
  - USearch HNSW with per-node fine-grained locking instead of one global mutex
nest steals: Steal the packed-metadata-byte + name-to-ID interning into nest-format. (1) In
             crates/nest-format/src/encoding add a 'varpack' codec for
             chunks/provenance/json-like sections: each scalar gets a 1-byte tag {type,
             len-width, int-width} so small ints and short strings shrink to 1-2 bytes vs fixed
             f32/u64 fields; additive (new encoding id in reserved 4-255), deterministic. (2)
             Add a name-to-ID mapper section (new reserved section id 0x09+) interning repeated
             provenance keys, model fingerprints, metadata field names to u16 IDs, dictionary
             stored once, IDs per record; deterministic via alphabetical key order. (3) In
             nest-runtime apply the single-store reference pattern: bm25/hnsw sidecars reference
             chunk_ids by small interned IDs not re-embedded strings. (4) Adopt the
             section-offset table + batch-info idea for the nest-format manifest/reader so large
             sections seek (and later mmap-parse in parallel) without scanning. All four respect
             single-file/offline/deterministic/additive and fit the <=300-line codec-per-file
             rule.
compression: On-mission for "compress more than everyone" on NON-embedding sections
             (text/json/yaml/provenance/metadata) which nest currently treats as zstd-only.
             Packed-metadata-byte + varint + name interning is how to shrink small-integer-heavy
             and repeated-key-heavy structured payloads (provenance, spans, json/parquet
             datasets nest wants to ingest) before zstd, often beating generic zstd on
             structured data by removing per-record type overhead and key-string repetition.
             mmap-friendly, decode-cheap, does not touch the hot scoring path (embeddings stay
             raw/f16/int8). Single-store references also stop duplicating large blobs across
             index + payload, shrinking hybrid/tiny presets.
perf:        In-memory engine targets sub-millisecond traversals; skip lists give O(log n) lock-free reads,
             coordinated writes. Per-object RAM cost is high (Edge >=88B incl 56B Delta, Vertex
             >=136B) which is the opposite of nest's goal, so steal the on-disk encoding ideas
             NOT the in-RAM skip-list/delta layout. Snapshot write/recovery are batched and
             parallelized via a batch-info section. PropertyStore zlib compresses whole
             per-vertex property blobs (nest should keep zstd, applied AFTER varpack). USearch
             HNSW uses per-node fine-grained locks; nest's HNSW is single-threaded deterministic
             build, so reference-only.
