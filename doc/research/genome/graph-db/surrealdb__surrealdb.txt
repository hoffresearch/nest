what:        SurrealDB is a Rust multi-model (document/graph/vector/full-text) database that layers SurrealQL
             over pluggable sorted KV backends (RocksDB/SurrealKV/TiKV/FDB), built on two
             reusable in-house encoding crates: `revision` (revision-tolerant binary
             serialization for schema evolution) and `storekey` (order-preserving lexicographic
             key encoding).
innovation:  The `revision` crate: a `#[revisioned(revision = N)]` derive macro that prefixes every
             serialized struct/enum with a varint revision number, then uses per-field
             attributes (`start = N`, `end = N`, `convert_fn`, `default_fn`) so bytes written by
             an older schema deserialize losslessly into the newest in-memory type via declared
             migration/default functions. This makes binary records forward/backward compatible
             WITHOUT a format-version bump and without a self-describing schema in each record
             -- the version tag is one varint, fields stay positional. It separates a cheap
             additive field-add (default_fn) from a true breaking change (convert_fn), which is
             exactly nest's v1-additive vs v2-breaking distinction, but expressed at per-field
             granularity instead of per-file.
techniques:
  - revisioned macro: leading varint u16 revision tag per record + positional
    (non-self-describing) field layout, so the schema lives in code not in bytes
  - per-field lifecycle attributes start=N / end=N with convert_fn (old->new migration) and
    default_fn (fill new fields) -- additive vs breaking encoded per field
  - optimised envelope: u16 revision varint | u32_le payload_length | optional field offsets |
    fields, enabling O(1) skip of whole records
  - SkipRevisioned / WalkRevisioned traits: consume-without-allocate skip and per-element walk
    to seek one field/blob without decoding the rest (lazy partial decode off a buffer)
  - specialised-vectors bulk encoding for Vec<primitive>/Vec<Uuid>/Vec<Decimal> (contiguous, no
    per-element framing) vs per-element framing for sets/heaps
  - storekey: order-preserving binary key codec where lexicographic byte order == logical order
    (sign-flip signed ints, IEEE754 float bit-twiddle, null-escaped strings), aiming for fewest
    bytes
  - hierarchical key construction (ns -> db -> tb -> id) so every logical scope is a contiguous
    byte-range prefix scan; prefix()/suffix() range mappers per item type
  - HNSW/DiskANN low-precision storage TYPE clause (F32/F16/I8/U8) -- quantization is a
    per-index storage-type choice decoupled from the distance metric
nest steals: Adopt the `revision` pattern in nest-format for the manifest and future binary sub-records,
             augmenting today's JCS canonical-JSON manifest
             (crates/nest-format/src/manifest/canonical.rs). Concretely: give each reserved
             section (ids 0x09+) and each future manifest field a `start = N` revision tag so a
             v1 reader can skip-or-default unknown additive fields deterministically -- turning
             nest's prose rule ('additive-only within v1; bump NEST_FORMAT_VERSION only on
             meaning change') into machine-checked per-field metadata, and crucially
             distinguishing a default_fn add (stays v1) from a convert_fn change (forces a true
             v2). The SkipRevisioned/WalkRevisioned traits map onto nest-runtime's mmap hot
             path: lazily walk a section to one chunk's span without decoding neighbors,
             complementing reader/parse.rs. Separately, steal `storekey` order-preserving
             encoding for nest-format/src/sections/chunk_ids.rs and any future sorted index
             (e.g. a chunk_id->offset table or a graph-edge section): sign-flipped/escaped
             lexicographic keys enable prefix range-scans and let monotonic ids be delta+varint
             compressed far tighter than raw u64 arrays, directly serving 'compress more than
             everyone'. Both are pure codecs: deterministic (positional layout + canonical
             order) and offline (no socket), respecting nest's hard constraints; keep each new
             rust file <=300 lines.
compression: Real but layered. `revision`'s positional non-self-describing layout plus a one-varint version
             tag is far more byte-frugal than nest's JSON manifest and gives compatibility for
             free, removing per-record schema overhead. `storekey`'s order-preserving +
             minimal-byte key encoding is the directly compression-relevant piece: sorted,
             sign-flipped, escaped keys make chunk_ids and any index section delta-encodable and
             varint/zstd-friendly (monotone ids compress near-entropy), and the prefix-scan
             hierarchy avoids storing redundant high-order key bytes. DiskANN's per-index
             F16/I8/U8 storage type confirms nest's tiny-preset int8 quantization is mainstream.
perf:        revision uses bincode under the hood; specialised-vectors gives contiguous bulk encode/decode
             for Vec<primitive> (fast, cache-friendly) but its walk path rejects each element
             before reading length (must use DeserializeRevisioned/SkipRevisioned there). The
             u32_le payload_length + optional offset table enables O(1) record skip and
             selective field decode -- good for mmap partial reads. storekey targets minimal
             byte count, keeping key sections small and zstd-friendly. SurrealDB 3.0 added a
             streaming/batched execution engine and concurrent HNSW writes; DiskANN (DEGREE 64,
             L_BUILD 100, ALPHA 1.2) targets larger-than-memory graphs -- not needed by nest's
             single-file in-memory model but validates int8 quantization.
license:     SurrealDB core: BSL 1.1 (converts to Apache-2.0 after ~4 years). The reusable sub-crates
             `revision` and `storekey` are permissive (Apache-2.0 / MIT) -- safe to vendor or
             depend on for nest-format. Verify exact SPDX before vendoring.
