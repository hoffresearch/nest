================================================================================================
synthesis :: graph-db
graph databases, engines, and traversal
================================================================================================

state of the art and concrete nest recommendations for this category.

summary:     Across 13 graph engines the single convergent idea is: compress structured integer/ID streams
             (adjacency lists, ID columns, postings) with sort -> delta -> minimum-bit-width
             packing, and keep them searchable/traversable WITHOUT decoding by mmapping a flat
             CSR layout. Every serious engine (Neo4j, GDS, Kuzu, GraphScope/GraphAr, JanusGraph,
             Nebula, TuGraph) lands on the same Pareto winner over varint+zstd for monotone
             columns; Dgraph's sroar pushes it further (the compressed bytes ARE the in-memory
             layout, zero decode tax - exactly nest's hot-path rule); Kuzu's ALP is the lone
             idea that legitimately challenges nest's "never compress embeddings" axiom with a
             LOSSLESS float codec that still decodes to exact bits for SIMD scoring. FalkorDB
             contributes per-section density-tiered codec auto-selection (iso/bitmap/sparse),
             Blazegraph contributes front-coding that is binary-searchable on compressed bytes
             (ideal for nest's alphabetical bm25 vocabulary and sha256 chunk_ids), and
             VPack/Memgraph/TypeDB contribute packed-metadata-byte + key-interning for the
             structured/json payloads nest wants to ingest next. nest currently stores all of
             these as raw or zstd: HNSW neighbor lists as fixed u32 (ann/codec.rs:30), bm25
             postings as raw u32 doc/tf pairs (bm25/codec.rs:33-36), spans as raw u64 pairs.
             Grounding correction to the extracts: nest's chunk_ids are sha256:<hex> STRINGS not
             dense ints, so the dense-ordinal delta trick applies to the implicit 0..N row index
             (HNSW/graph/bm25 doc ids) and to span offsets, not to chunk_ids values directly;
             front-coding is the right codec for the sha256 strings. The mission-critical
             sequence: (1) ship one delta+bitpack integer-stream codec in encoding/ (reserved id
             0x04..0xFF), (2) re-encode hnsw_index and bm25_index postings with it, (3) add a
             CSR graph_adjacency section (0x09) reusing it for the north-star graph-search gap,
             all additive within format v1, all deterministic, none touching the embedding hot
             path. Then evaluate ALP as the high-risk/high-reward lossless embedding path.

state of the art
------------------------------------------------------------------------------------------------
The field has converged on a single canonical recipe for graph/ID storage: sort target IDs
ascending, delta-encode into small monotone gaps, then bit-pack per fixed-size block to the
minimum bit width the local maximum needs ("integer packing" / PForDelta family), laid out as
flat CSR (offsets array + degrees + packed-targets blob). This beats both global encodings and
per-value continuation-bit varints on the speed/ratio Pareto front because block unpack is
branchless, cache-local and SIMD-friendly, and crucially it is mmap-pure: no dictionary/window
state, decodes a single block in place off disk (Neo4j, GDS report ~6x over uncompressed at
memcpy decode speed; GraphAr reports 27% of plain+offset; GDS ~1.4 bytes/edge). The frontier
idea is making the compressed representation directly operable: Dgraph's sroar serialized
roaring bitmaps run set-intersection (graph join = bitmap AND) with zero unmarshal (~7x faster,
~15x less memory than reference roaring); FalkorDB auto-selects the most compact of four sparse
tiers per matrix plus an iso single-scalar mode for boolean adjacency; Blazegraph front-codes
sorted keys so they stay binary-searchable on the compressed bytes (search-on-compressed, no
inflate). For the float problem specifically, Kuzu's ALP/ALPRD is state-of-the-art lossless
float compression (beats Gorilla/Chimp/Patas/Elf, matches/beats zstd, far faster,
auto-vectorizing 1024-value blocks) and is the only credible path to compress embedding-grade
arrays while keeping exact in-place SIMD scoring. For structured/document payloads the consensus
is self-describing trailing-offset tables with smallest-width offset selection plus a per-file
key dictionary (VPack ~2-3x on repeated-schema json; Memgraph/TypeDB packed-metadata-byte + name
interning). Licensing reality: the algorithms (delta, varint, bit-packing, CSR, front-coding,
roaring) are decades-old public-domain; the GPL/BSL/SSPL engines (Neo4j, GDS, memgraph,
FalkorDB, blazegraph) are learn-from-only, while Kuzu (MIT), GraphScope/GraphAr, JanusGraph,
Nebula, TuGraph, sroar/badger (Apache-2.0) and SurrealDB's revision/storekey sub-crates
(MIT/Apache) are clean-room or vendorable references.

top transferable innovations
------------------------------------------------------------------------------------------------
1. Delta + per-block minimum-bit-width integer packing (PForDelta family) over sorted ID
   streams: the universal codec that beats zstd on monotone integers at memcpy decode speed and
   is mmap-seekable per-block. Drawn from Neo4j integer packing, GDS PackedAdjacencyList,
   GraphAr delta CSR, TuGraph length-varint. This is the single highest-value steal: nest stores
   HNSW neighbor lists, bm25 postings and span offsets uncompressed/zstd today, and all three
   are textbook inputs.
2. Flat CSR adjacency (u64 offsets array + packed neighbor-id blob) as a frozen,
   mmap-traversable graph section: one node's neighbors are a single contiguous slice walked
   with zero allocation, identical discipline to nest's embedding rows. Drawn from Neo4j/GDS
   CSR, Nebula prefix-locality, Kuzu disk-CSR, GraphAr, TuGraph. This is the concrete delivery
   vehicle for nest's named graph-search north-star gap.
3. ALP / ALPRD lossless float compression decoded in-register before SIMD dot-product: the only
   idea that challenges nest's 'embeddings can never be compressed' axiom while keeping
   exact-cosine rerank byte-true. Drawn from Kuzu (MIT, vendorable). Highest payoff (embeddings
   are the dominant byte cost and the largest section) but highest risk to the hot path.
4. Serialized roaring bitmaps where the compressed bytes ARE the in-memory layout, enabling
   set-intersection with zero decode: matches nest's no-decode-on-hot-path rule exactly. Drawn
   from Dgraph sroar (Apache-2.0). Best fit for bm25 postings (term -> sorted doc-id set) and a
   boolean chunk-to-chunk graph.
5. Per-section density-tiered codec auto-selection driven by measured min/max/cardinality stats
   (raw vs delta-pack vs roaring vs iso-single-scalar), chosen deterministically at build time.
   Drawn from FalkorDB 4-tier sparse + iso, Kuzu per-chunk adaptive codec, GraphAr. Raises
   nest's compression ceiling for EVERY section, not just graphs, replacing today's per-preset
   hardcoding.
6. Front-coding (every Nth sorted key full, rest as shared-prefix-len + suffix) that stays
   binary-searchable on the compressed bytes: search-on-compressed with no inflate. Drawn from
   Blazegraph raba coders (learn-only, GPL). Ideal for nest's sha256:<hex> chunk_ids and the
   alphabetically-ordered bm25 term dictionary.
7. VPack trailing-offset-table + smallest-width offset selection + object-key dictionary for
   structured/json payloads: zero-parse random sub-document access off mmap plus 2-3x shrink on
   repeated-schema corpora. Drawn from ArangoDB VelocyPack (Apache-2.0), reinforced by Memgraph
   packed-metadata-byte and TypeDB inline-vs-hash. The codec for nest's json/yaml/parquet ingest
   roadmap.
8. SurrealDB revision pattern (leading varint version tag + positional non-self-describing
   fields with per-field start=N/default_fn vs convert_fn): turns nest's prose
   'additive-within-v1 vs true-v2' rule into machine-checked per-field metadata, far more
   byte-frugal than the current JSON manifest. revision/storekey sub-crates are MIT/Apache,
   vendorable.
9. Inline distance co-location: store the f16/int8 edge distance inline next to each neighbor id
   in the CSR adjacency so graph expansion skips a separate distance array lookup. Drawn from
   Nebula rank-as-sort-key, Kuzu. Cache-locality win for the future graph traversal kernel.
10. Order-preserving / sort-as-index byte layouts (lexicographic byte order == logical order) so
   range scans need no separate index. Drawn from JanusGraph edge-as-cell, TypeDB memcmp keys,
   storekey. Reinforces nest's determinism: canonical sort + delta layout is inherently
   content_hash-stable.

nest recommendations
------------------------------------------------------------------------------------------------
* Add one delta + zigzag + minimum-bit-width block-packing integer-stream codec as a new module
  crates/nest-format/src/encoding/intpack.rs (delta -> zigzag for signed gaps -> pack each fixed
  block of N=128 to ceil(log2(max_in_block)) bits, with a tail strategy for the final partial
  block). Register it as a new SECTION encoding id in the reserved 0x04..0xFF space (next free
  after int8=3, e.g. 0x05) and wire it into decode_payload() in encoding/mod.rs. Pure function
  of sorted input, no dictionary state, thiserror-typed, never panics, under 300 lines.
    where:  crates/nest-format/src/encoding/intpack.rs (new) + register in encoding/mod.rs decode_payload
            (currently matches RAW/ZSTD/FLOAT16/INT8 at lines 44-55) + new const
            SECTION_ENCODING_INTPACK in layout/mod.rs (next to lines 211-214). Apply to
            chunks_original_spans byte_start/byte_end u64 columns first.
    impact: high
    effort: medium
    from:   neo4j/neo4j, neo4j/graph-data-science, alibaba/GraphScope, TuGraph-family/tugraph-db,
            vesoft-inc/nebula

* Re-encode the HNSW neighbor lists with the intpack codec instead of fixed u32. In ann/codec.rs
  to_bytes() (lines 24-34) neighbor ids per node/layer are written as raw u32; sort each
  neighbor list, delta+bitpack it, and store per-list bit-width. This directly shrinks the
  hnsw_index(0x07) section that the 'tiny' preset (0.283 ratio) already ships, with zero recall
  impact (neighbor SET is unchanged, only its byte encoding) and a branchless unpack on read in
  from_bytes (lines 40-89).
    where:  crates/nest-runtime/src/ann/codec.rs to_bytes/from_bytes (HNSW_PAYLOAD_VERSION stays 1; this is
            an internal section re-encoding, additive). Reuse the intpack kernel from
            nest-format.
    impact: high
    effort: medium
    from:   neo4j/neo4j, kuzudb/kuzu, neo4j/graph-data-science

* Re-encode bm25_index postings as delta-coded doc-id runs (and optionally serialized roaring
  bitmaps for high-df terms). In bm25/codec.rs to_bytes() (lines 33-36) each term's postings are
  raw u32 doc + u32 tf; the doc ids within a term are already implicitly ascending, so
  delta+varint the doc column and bitpack tf. The alphabetical term order (already mandated for
  determinism, lines 26-28) makes this a pure deterministic re-encode. Shrinks the hybrid
  preset's bm25 section materially.
    where:  crates/nest-runtime/src/bm25/codec.rs to_bytes/from_bytes. For dense terms, a sroar-style bitmap
            whose bytes equal the in-memory layout lets the fusion path (bm25/fusion.rs) run
            posting intersections with no decode.
    impact: high
    effort: medium
    from:   dgraph-io/dgraph (with companion repos dgraph-io/sroar and dgraph-io/badger),
            blazegraph/database, alibaba/GraphScope

* Add an optional CSR graph_adjacency section (new section id 0x09, additive within v1) holding
  chunk-to-chunk edges (semantic-neighbor graph, citation links, or serialized HNSW level-0
  adjacency): a u64 offsets array indexed by chunk ordinal + a delta+bitpacked neighbor-id blob
  (reusing intpack), optionally with inline f16/int8 edge distances co-located per neighbor. Add
  a graph::CsrIndex reader in nest-runtime beside ann::HnswIndex that mmaps offsets and unpacks
  one node's run branchlessly, feeding candidates into the EXISTING mandatory exact-cosine
  rerank (search.rs score_subset) so graph traversal is a candidate generator, never a score
  source - identical contract to HNSW.
    where:  new SECTION_GRAPH_ADJACENCY=0x09 in layout/mod.rs (after BM25=0x08, line 234) +
            OPTIONAL_SECTIONS list (lines 256-258); new crates/nest-runtime/src/graph/ module
            (mod.rs + csr.rs, each <300 loc); new nest-cli subcommand search-graph mirroring
            search-ann. Delivers the named graph-search north-star gap.
    impact: high
    effort: high
    from:   vesoft-inc/nebula, TuGraph-family/tugraph-db, alibaba/GraphScope, neo4j/neo4j, apache/tinkerpop

* Add deterministic per-section codec auto-selection driven by measured statistics: at build
  time compute min/max/cardinality/monotonicity for each non-embedding section and pick the
  smallest of {raw, zstd, intpack, roaring, iso-single-scalar} rather than a fixed per-preset
  choice. Record the chosen encoding id per section (already supported by the manifest's
  per-section encoding field). Iso mode stores ONE scalar when all values are identical (e.g.
  unweighted/boolean adjacency).
    where:  build-time codec chooser in crates/nest-format/src/writer/ (Python build stage feeds stats);
            selection is a pure function of section bytes so content_hash stays stable. Each
            section's encoding already lives in SectionEntry, so this is additive.
    impact: medium
    effort: medium
    from:   FalkorDB/FalkorDB, kuzudb/kuzu, alibaba/GraphScope

* Front-code the sha256:<hex> chunk_ids section and the alphabetical bm25 term dictionary: every
  Nth sorted key stored full, the rest as (shared_prefix_len varint, suffix), plus a tiny offset
  table to binary-search the full keys. sha256 hex strings share long common prefixes after
  sorting and the bm25 vocabulary is already alphabetical, so both shrink losslessly AND stay
  binary-searchable on the compressed bytes (no decompress on the search/cite path). New
  encoding id in the reserved range, applied only to these sorted-string sections.
    where:  crates/nest-format/src/encoding/frontcode.rs (new, <300 loc) applied in sections/chunk_ids.rs
            (currently plain length-prefixed strings, lines 8-15) and bm25/codec.rs term
            dictionary. Enables nest://content_hash/chunk_id resolution via memcmp prefix scan
            instead of a hashmap.
    impact: medium
    effort: medium
    from:   blazegraph/database, typedb/typedb

* Build a VPack-style structured-payload codec for the json/yaml/parquet ingest roadmap: a
  [tag][smallest-width 1/2/4/8 LE offsets][values] trailing-offset-table layout plus a per-file
  object-key dictionary (collect+count keys, intern repeated keys to u16 ids, sorted bytewise
  for determinism). Enables mmap sub-path resolution (doc.field[3].name) with pure base+offset
  arithmetic and zero decode, complementing zstd (store VPack-encoded, optionally zstd the cold
  parts). 2-3x on repeated-schema corpora like the PT-BR datasets.
    where:  new crates/nest-format/src/encoding/vpack.rs + a structured-document section id 0x0a; the
            key-dictionary two-pass runs in the Python build stage, the Rust serve path only
            does base+offset reads. Reinforced by Memgraph packed-metadata-byte (1-byte
            {type,len-width,int-width} tag) for scalar columns.
    impact: medium
    effort: high
    from:   arangodb/arangodb (core innovation lives in https://github.com/arangodb/velocypack),
            memgraph/memgraph, typedb/typedb

* Evaluate ALP/ALPRD as a LOSSLESS embeddings codec (new dtype/encoding for section 0x04) that
  decodes per 1024-value block in-register immediately before the SIMD dot product, so the
  exact-cosine rerank in search.rs stays byte-true. This is the only path to compress nest's
  largest section without the lossiness of today's float16/int8. Gate it behind a benchmark
  proving the fused ALP-decode+dot kernel does not regress search latency past the boot-overhead
  budget; keep the scalar auto-vectorizing kernel under 300 loc per simd file.
    where:  crates/nest-runtime/src/simd/ (new alp_dot path beside avx2.rs/neon.rs/scalar.rs, dispatched in
            simd/mod.rs) + ALP encode in nest-format/encoding for SECTION_EMBEDDINGS (0x04).
            Highest reward, highest risk; do AFTER the integer-codec wins land and only if
            benchmarks pass. Kuzu is MIT so the kernel can be ported clean.
    impact: high
    effort: high
    from:   kuzudb/kuzu, surrealdb/surrealdb

* Adopt the SurrealDB revision pattern for the manifest and future binary sub-records: a leading
  varint version tag + positional fields with per-field start=N (additive, default_fn => stays
  format v1) vs convert_fn (meaning change => forces true v2). This makes nest's prose
  'additive-only within v1, bump NEST_FORMAT_VERSION only on meaning change' machine-checked
  per-field, and is far more byte-frugal than the current canonical-JSON manifest.
  revision/storekey are MIT/Apache (vendorable after SPDX check).
    where:  crates/nest-format/src/manifest/ (canonical.rs currently JCS-canonical JSON); add a binary
            revisioned envelope option. Pure positional layout keeps determinism; no socket,
            offline-safe.
    impact: low
    effort: medium
    from:   surrealdb/surrealdb, apache/tinkerpop

* When the CSR graph section ships, support a delta-plus/delta-minus overlay for the planned
  real-time edit: keep the frozen mmap'd adjacency immutable and merge a tiny
  pending-add/pending-delete overlay at read time, flushing to a new deterministic container on
  commit. Preserves single-file + determinism (the committed file is always a clean
  re-serialize, the overlay never persists into the canonical bytes).
    where:  crates/nest-runtime/src/graph/ overlay reader (read-time three-way merge), with commit going
            through the normal nest-format writer so content_hash is recomputed canonically.
            Reference design only until real-time edit is on the roadmap.
    impact: low
    effort: high
    from:   FalkorDB/FalkorDB, memgraph/memgraph

compression wins
------------------------------------------------------------------------------------------------
  - chunks_original_spans byte_start/byte_end: u64 pairs that are locally monotone (byte offsets
    into source docs). Delta+zigzag+bitpack collapses these from 16 bytes/span toward 1-3
    bytes/span losslessly, decode at memcpy speed off mmap (vs raw today). First and cheapest
    intpack target - pays off before any graph work.
  - hnsw_index(0x07) neighbor lists: currently fixed u32 per neighbor (ann/codec.rs:30-31).
    Sort+delta+bitpack each list to ceil(log2(max_gap)) bits - GDS reports ~6x on adjacency;
    directly improves the tiny preset's 0.283 ratio with zero recall change (the neighbor SET is
    identical, only its encoding shrinks).
  - bm25_index(0x08) postings: raw u32 doc + u32 tf pairs (bm25/codec.rs:33-36) with doc ids
    already implicitly ascending. Delta-code the doc column and bitpack tf; for high-df terms
    switch to a serialized roaring bitmap (sroar-style, bytes==memory layout) so fusion runs
    posting AND with no decode. Shrinks the hybrid preset and speeds fusion.
  - chunk_ids sha256:<hex> strings: after sorting, the hex strings share long common prefixes -
    front-coding (every Nth full, rest as shared-prefix-len+suffix) is lossless, stays
    binary-searchable on compressed bytes, and shrinks a section that currently stores 70+ bytes
    per id raw. Correction to the extracts: chunk_ids are strings not dense ints, so
    front-coding (not delta) is the right codec here.
  - Future graph_adjacency(0x09) section: delta+varint CSR is proven at 27% of plain+offset
    (GraphAr); with FalkorDB iso mode an unweighted/boolean chunk graph costs ~N row-indices +
    offsets + ONE value scalar. Adds graph search to the mission at near-zero extra bytes,
    keeping the .nest container compact.
  - Structured json/yaml/parquet ingest (roadmap): VPack key-dictionary + smallest-width offsets
    gives 2-3x on repeated-schema data like the PT-BR datasets while preserving zero-decode
    random field access - the compress-AND-serve combination, beating naive zstd-of-json on
    access cost. Composes with zstd on the cold parts.
  - provenance(0x05) JSON blob + repeated metadata keys: name-to-id interning (Memgraph/VPack)
    replaces repeated long keys/model-fingerprints with u16 ids, deterministic via alphabetical
    key order; shrinks the structured metadata before zstd.
  - Embeddings(0x04), the dominant byte cost and the section nest currently refuses to compress:
    ALP/ALPRD is the only LOSSLESS path that keeps exact in-place SIMD scoring (decodes to exact
    bits per 1024-block in-register before the dot product), advancing
    compress-more-than-everyone past today's LOSSY float16/int8 - gated on a
    no-latency-regression benchmark.

watch-outs (conflict with nest constraints)
------------------------------------------------------------------------------------------------
  - Do NOT vendor source from GPL/BSL/SSPL engines: Neo4j + GDS (GPLv3), memgraph (BSL 1.1),
    FalkorDB core (SSPL), blazegraph (GPLv2). These are learn-from-only. The underlying
    algorithms (delta, varint, bit-packing, CSR, front-coding, roaring) are decades-old
    public-domain and must be clean-room reimplemented from spec. Safe to port/vendor: Kuzu
    (MIT), sroar/badger + GraphScope/GraphAr + JanusGraph + Nebula + TuGraph (Apache-2.0),
    SurrealDB revision/storekey sub-crates (MIT/Apache - verify SPDX first). VPack is Apache-2.0
    (the ArangoDB server moved to BSL but the format lib/spec did not).
  - NEVER apply the integer codec, roaring, or zstd to the embeddings section on the current hot
    path - they require decode/window state and would break the score-directly-from-mmap rule.
    The ONLY embedding-compression candidate is ALP because it decodes to EXACT bits in-register
    per block; even then it must be benchmarked against the search-latency budget before
    landing, and the search contract's mandatory exact-cosine rerank must remain byte-true.
  - Block/page co-location and alignment (Neo4j Block format, Kuzu 4KB pages) can use MORE disk
    than tightly-packed layouts due to padding/headers - directly against nest's size-first
    goal. Take the integer codec and CSR layout, NOT the page-padding. Likewise reject the
    in-RAM structures (memgraph skip-lists, Edge>=88B / Vertex>=136B; TypeDB auto-built
    bidirectional indices ~24GB vs 17GB) - those optimize RAM/write, the opposite of nest's
    compact read-only file.
  - Skip every server/LSM/multi-file storage engine wholesale: Badger (Dgraph), RocksDB
    (TypeDB/Nebula/SurrealDB backends/ArangoDB), LMDB (TuGraph), Redis modules (FalkorDB),
    Cassandra/HBase (JanusGraph), Gremlin Server/OLAP/Spark (TinkerPop). They violate
    single-file/offline/no-socket. Only the on-disk byte-layout discipline transfers.
  - Determinism must hold for every new codec: bit-packing block size must be FIXED, sort order
    canonical (ascending ids / alphabetical terms - already nest's rule), roaring container
    choice is a pure function of cardinality, no entropy-coder dictionary state. content_hash
    must stay STABLE across encodings - so decode-then-hash must yield identical canonical bytes
    regardless of whether intpack/roaring/front-code was used (mirror the existing 'content_hash
    hashes decoded bytes' rule in encoding/mod.rs lines 15-18).
  - Endianness: GraphBinary (TinkerPop) is big-endian and many graph engines use big-endian keys
    for lexicographic ordering - nest mandates little-endian unsigned everywhere. Adapt the
    layout, do not copy byte order. For order-preserving keys, replicate storekey's
    sign-flip/IEEE754-twiddle in LE rather than relying on raw BE byte order.
  - File-hygiene: each new codec (intpack, frontcode, vpack, alp) must be a
    single-responsibility file <=300 lines (333 hard cap), repr(C), all integers LE-unsigned,
    typed thiserror errors, never panic in library code. The graph module must split
    mod.rs/csr.rs/overlay to respect the cap.
  - Two-pass build-time costs (VPack key dictionary, sort+id-assignment, FalkorDB stat-driven
    codec selection, front-code offset tables) are acceptable in the Python BUILD stage but must
    NEVER appear on the Rust serve path. Keep the runtime to mmap + branchless unpack + dot
    product. Beware the search-text ~300-500ms python boot overhead is already a known gap - do
    not add per-query planning cost (TinkerPop notes strategy application costs ~5-6x bytecode
    construction; run any graph query rewrite ONCE at plan time, not per-traverser).
  - Roaring/sroar zero-decode benefit only materializes if the on-disk container layout EQUALS
    the in-memory layout with correct LE alignment; a naive roaring port that requires an
    unmarshal step loses the entire hot-path advantage and is then just worse zstd. Mirror
    sroar's single-buffer contract exactly or use plain delta+bitpack instead.
