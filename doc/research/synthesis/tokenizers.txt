================================================================================================
synthesis :: tokenizers
tokenization (the front of every embed + a compression primitive)
================================================================================================

state of the art and concrete nest recommendations for this category.

summary:     Across HF tokenizers, SentencePiece, tiktoken, and OpenNMT Tokenizer the field has converged on
             one shape that is almost custom-built for nest's north star: a tokenizer is a
             self-contained, frozen, deterministic, reversible compression codec. The shared
             primitives are (a) a byte-level alphabet (GPT-2/tiktoken bijective
             256-byte<->printable-Unicode map, or SentencePiece byte_fallback emitting <0xNN>)
             that makes ANY input -- CJK, Thai, emoji, JSON, YAML, PDF-text, binary --
             losslessly tokenizable with zero UNK; (b) a learned variable-length dictionary
             code, either grow-by-merge BPE (HashMap<(u32,u32)->rank> integer-pair merges,
             greedy lowest-rank) or shrink-by-prune Unigram-LM (Viterbi best-path over a lattice
             scored by log-probs, O(n) memory); (c) reversible surface markup (U+2581 spacer /
             U+FFED joiner / case channel) so detokenization is a pure string op and the
             round-trip is byte-exact; (d) compact mmap-resident lookup structures
             (SentencePiece Darts double-array trie holds 80k pieces in ~2MB vs ~83MB of pointer
             tries, just integer base[]/check[]/value[] arrays read straight off disk); (e) full
             (start,end) offset alignment back into the ORIGINAL string surviving destructive
             NFKC/lowercase/strip normalization; and (f) one version-tagged self-describing
             artifact (tokenizer.json / ModelProto) carrying the entire pipeline. The crucial
             reframing for nest: token-id streams ARE compression -- they replace multi-byte
             UTF-8 runs with dense small integers BEFORE zstd, and because the dictionary is
             trained ON the corpus it captures domain morphemes (PT-BR news, JSON keys, code)
             that generic zstd cannot model. Stacking range/zstd on the id stream compounds the
             win. This is the single most mission-relevant external category for 'compress more
             than everyone' on text-bearing sections, and it simultaneously closes the
             documented CJK/Thai bm25 gap with the same shipped model. Hard caveat repeated by
             every extract: NEVER apply to the embeddings section -- the hot-path SIMD cosine
             kernel scores raw f32/f16/int8 straight off mmap and tokenization would destroy
             that.

state of the art
------------------------------------------------------------------------------------------------
The state of the art is a unified pipeline normalizer -> pre-tokenizer -> model ->
post-processor -> decoder, where the 'model' is a learned variable-length dictionary over a
CLOSED byte-level alphabet, serialized as a single frozen self-describing artifact and decoded
by a tiny integer-indexed structure. Two training philosophies, one runtime shape. BPE
(tiktoken, HF, OpenNMT) grows a vocab by greedily merging the lowest-rank adjacent byte-pair;
merges are stored as integer (u32,u32)->rank HashMaps (no string compares), decode is
HashMap<rank,Vec<u8>> concat, fully deterministic and seedless. Unigram-LM (SentencePiece, HF)
starts from a large suffix-array-seeded vocab and prunes by EM (shrinking_factor 0.75) until
target size; segmentation is Viterbi over a lattice storing only best-path score+backpointer per
char position (O(n) memory, recognized-then-discarded lattice nodes), giving provably
minimum-cost segmentation. Losslessness on arbitrary bytes is universal via byte-level bijection
(tiktoken/GPT-2) or byte_fallback to 256 raw-byte pieces (SentencePiece type=6) -- zero
out-of-vocab loss, the property nest's lossless/reversible/content_hash-stable guarantees
demand. Reversibility is achieved with in-band markup (U+2581 whitespace meta-symbol, U+FFED
joiner, case channel) so the original reconstructs byte-exactly. The runtime lookup is the Darts
double-array trie (base/check/value/score parallel arrays, transition next=base[node]+byte
validated by check[next]==node, plus first_byte_max_len[256] early termination) -- 80k pieces in
~2MB, pointer-light integer indexing ideal for repr(C)+LE+mmap+never-panic, and it does NOT
contend with the AVX2/NEON dot-product path (trie traversal is branch-bound, not a SIMD kernel).
Perf is excellent and build-time only: tiktoken 3-6x faster than HF on 1GB GPT-2 text, HF
~1GB/CPU-min (<20s/GB), SentencePiece ~50k sentences/sec with ~6MB footprint, all pure scalar
Rust/C++ with no SIMD in the tokenizer. Offset-alignment tracking (every token carries
(start,end) byte offsets into the original even through destructive normalization) is the proven
design for span-exact citations. Determinism is native: BPE merge-rank order and Unigram
seeded-EM + stable tie-break (leftmost) make builds reproducible, which maps cleanly onto nest's
bm25 alphabetical-term-order and seeded-hnsw discipline.

top transferable innovations
------------------------------------------------------------------------------------------------
1. Byte-level closed alphabet (tiktoken/GPT-2 bijective 256-byte<->Unicode map; SentencePiece
   byte_fallback type=6 pieces): makes tokenization lossless and reversible on ANY input with
   zero UNK -- the non-negotiable property that lets a learned dictionary code satisfy nest's
   lossless/content_hash-stable/language-agnostic guarantees, and the direct fix for the
   CJK/Thai bm25 gap.
2. Token-id stream as dictionary compression front-end: a learned BPE/Unigram vocab turns
   multi-byte UTF-8 runs into dense small integers BEFORE entropy coding, and because it is
   trained ON the corpus it models domain morphemes (PT-BR news, JSON keys, code) that generic
   zstd cannot. The single most mission-relevant idea for compress-more-than-everyone on
   text-bearing sections.
3. SentencePiece Darts double-array trie: 80k pieces in ~2MB (vs ~83MB pointer tries) as plain
   integer base[]/check[]/value[]/score[] arrays read straight off mmap -- a perfect
   repr(C)+LE+never-panic decoder that keeps the tiny/portable mandate and never touches the
   SIMD cosine path.
4. Unigram-LM Viterbi best-path segmentation: O(n)-memory minimum-cost (most-probable)
   segmentation over a lattice, provably better symbol assignment than greedy BPE for
   compression, with seeded-EM determinism so byte-identical builds hold.
5. Reversible in-band markup (U+2581 spacer / U+FFED joiner / case channel from
   OpenNMT+SentencePiece): detokenization is a pure string replace, so token-id codec
   round-trips byte-exact and content_hash over decoded canonical text stays stable -- no
   separate span storage needed for reconstruction.
6. Integer (u32,u32)->rank merge tables (tiktoken/HF): pair-rank HashMap lookups, no string
   compares, seedless-deterministic greedy lowest-rank merge -- a ~150-200 loc pure-safe Rust
   merge loop that fits the 300-line file rule and the no-panic constraint.
7. Offset/alignment tracking through destructive normalization (HF (start,end) byte offsets
   surviving NFKC/lowercase/strip): the proven design to harden chunks_original_spans so
   nest://content_hash/chunk_id stays byte-exact after lossy normalization.
8. Single self-describing version-tagged artifact (tokenizer.json / proto2 ModelProto carrying
   normalizer+model+decoder): mirror inline in nest's manifest so the file stays
   self-describing, offline, and reconstructs the exact pipeline with no external dependency.
9. Word-result LRU + per-thread cache (HF cache.rs, +47-62% on parallel workloads; OpenNMT lacks
   it and pays per-request): memoize per pre-token at build time so the BPE/Viterbi hot loop is
   amortized over repetitive corpora.
10. precompiled_charsmap (SentencePiece NFKC compiled to a double-array trie + rewrite string,
   layout [u32 trie_len][trie][normalized]): normalization-as-data-table not code, a frozen
   deterministic LE blob that fits nest's data-over-code, reproducible-build philosophy.

nest recommendations
------------------------------------------------------------------------------------------------
* Replace the naive is_alphanumeric word-splitter in bm25/tokenize.rs with byte-level subword
  segmentation (greedy BPE merge or Unigram Viterbi) driven by a frozen vocab, preserving
  lowercase + alphabetical term order for determinism. Closes the documented CJK/Thai
  degradation with zero format-breaking change.
    where:  crates/nest-runtime/src/bm25/tokenize.rs (currently 28 loc, the char-class splitter); vocab
            loaded once by bm25::Bm25Index at index build and search time. No section change
            required if vocab ships inline in the manifest; or read it from the new tokenizer
            section in rec 2.
    impact: high
    effort: med
    from:   https://github.com/openai/tiktoken, https://github.com/google/sentencepiece,
            https://github.com/huggingface/tokenizers

* Add a frozen tokenizer model as an optional additive v1 section (reserve next id 0x09) holding
  either a BPE merge table (integer (u32,u32)->rank arrays + reverse) or a Unigram
  vocab+log-scores, stored as a Darts double-array trie (repr(C), little-endian
  base[]/check[]/value[]/score[]) for mmap-resident O(n) decode. Section is per-section SHA-256
  checksummed and zstd'd via the existing non-embedding codec path. The same model feeds both
  rec 1 (bm25) and rec 3 (text codec) -- one artifact, two uses.
    where:  crates/nest-format/src/layout/mod.rs (add pub const SECTION_TOKENIZER_MODEL: u32 = 0x09
            alongside 0x07/0x08); crates/nest-format/src/sections/ new tokenizer.rs (<300 loc
            encode/decode mirroring bm25 codec.rs ByteCursor style); manifest gains a tokenizer
            descriptor so the file stays self-describing/offline.
    impact: high
    effort: med
    from:   https://github.com/google/sentencepiece, https://github.com/openai/tiktoken,
            https://github.com/OpenNMT/Tokenizer

* Add a token-id text codec as a new RESERVED wire encoding id (next free is 4; current ids are
  raw=0 zstd=1 f16=2 int8=3) for the chunks_canonical section ONLY: store text as
  varint/range-coded subword id streams instead of raw UTF-8, then optionally zstd on top.
  decode_payload reconstructs canonical UTF-8 via reversible markup so content_hash (which
  hashes DECODED bytes) is unchanged and citations stay byte-exact. Python (nest-python) trains
  the vocab offline with seeded EM / deterministic merges so builds remain byte-identical.
    where:  crates/nest-format/src/encoding/mod.rs decode_payload match arm (add SECTION_ENCODING_TOKENIZED
            = 4); crates/nest-format/src/encoding/ new tokenized_codec.rs (<300 loc, the
            read-only trie + Viterbi/merge decode); guard so encoding 4 is rejected for the
            embeddings section. Encode side trained in nest-python, emitted by writer/build.rs.
    impact: high
    effort: high
    from:   https://github.com/google/sentencepiece, https://github.com/openai/tiktoken,
            https://github.com/OpenNMT/Tokenizer, https://github.com/huggingface/tokenizers

* Adopt HF-style (start,end) byte-offset tracking THROUGH destructive normalization to harden
  chunks_original_spans, so canonical->original mapping survives NFKC/lowercase/strip and
  nest://content_hash/chunk_id reopens the exact original byte span even when the canonical text
  was normalized.
    where:  crates/nest-format/src/sections/spans.rs (OriginalSpan encode/decode) plus the
            chunking/normalization step in nest-python that produces chunks_canonical +
            chunks_original_spans; the alignment is computed at build time, no runtime cost.
    impact: med
    effort: med
    from:   https://github.com/huggingface/tokenizers, https://github.com/OpenNMT/Tokenizer

* Add a tiny new 'micro' / 'archive' preset that pairs the token-id text codec (encoding 4) with
  zstd on the id stream and int8/hnsw embeddings, targeting an even smaller size ratio than
  today's tiny (0.283) on repetitive PT-BR news corpora, while keeping exact-cosine-rerank
  ground truth intact.
    where:  preset definitions in writer/build.rs + nest-python build surface; expose via nest-cli (no new

            surface).
    impact: med
    effort: low
    from:   https://github.com/google/sentencepiece, https://github.com/openai/tiktoken

* Mirror the single self-describing artifact idea: keep the entire tokenizer config (normalizer

  state, so a .nest file remains fully self-describing and reconstructs the exact decode

    where:  crates/nest-format/src/manifest/mod.rs (Manifest struct + to_canonical_json) and

    impact: med
    effort: low

    where:  inside the encode path of the new tokenized_codec.rs (build-time only, not on the mmap

    impact: low
    effort: low

compression wins
------------------------------------------------------------------------------------------------
  - Token-id streams over a corpus-trained vocab replace multi-byte UTF-8 runs with dense small
    integers BEFORE zstd; on repetitive/structured corpora (PT-BR news, JSON keys, YAML, code)
    this lowers entropy-coder input vs raw bytes and the gain COMPOUNDS when zstd/range-codes
    the id stream -- the core lever for compress-more-than-everyone on text sections, and it
    composes with the existing zstd codec rather than replacing it.
  - Unigram-LM Viterbi gives provably minimum-cost (most-probable) segmentation, so the id
    assignment itself is information-theoretically tighter than greedy BPE -- fewer/denser
    symbols for the same lossless reconstruction.
  - Training the vocab ON the file's own corpus captures domain-specific morphemes (Portuguese
    inflections, dataset-specific tokens, repeated JSON schema keys) that a generic byte
    compressor like zstd cannot model, beating zstd-on-raw-bytes on exactly the
    structured/repetitive data nest targets.
  - The vocab cap (e.g. shrink-by-prune to a small target size) bounds dictionary size, so the
    per-file tokenizer section stays small (SentencePiece 80k pieces ~2MB trie) and the net size
    ratio improves for the tiny/micro presets rather than regressing.
  - Range/rANS coding the id stream (a natural next layer on top of dense ids) is the documented
    endgame BPE-ids -> entropy-coder; nest can stage this as encoding id 4 = tokenized, then
    later 5 = tokenized+range, all additive within v1.
  - Same shipped model serves double duty: the bytes spent on the tokenizer section are
    amortized across BOTH the text-compression codec AND the bm25 subword terms, so the marginal
    cost of closing the CJK/Thai gap is near zero once the codec ships.
  - Byte-level closed alphabet guarantees losslessness on json/yaml/pdf-text/binary, extending
    the compress-everything mandate (text, json, yaml, parquet, pdf, audio/video metadata) to a
    single reversible codec path without per-format special-casing.

watch-outs (conflict with nest constraints)
------------------------------------------------------------------------------------------------
  - NEVER tokenize the embeddings section. Every extract flags this: the hot path is SIMD cosine
    scoring raw f32/f16/int8 straight off mmap; token-id encoding would destroy random-access
    vector layout and the AVX2/NEON dot-product kernel. Enforce a hard guard that encoding id 4
    (tokenized) is rejected for the embeddings section in decode_payload / writer.
  - Determinism is the make-or-break constraint. EM training (Unigram) is iterative and
    tie-breaks matter; you MUST seed EM and use a stable leftmost tie-break (BPE is naturally
    seedless/deterministic, prefer it if EM determinism is hard to pin). Without bit-exact
    reproducibility the same chunks + same model fingerprint will NOT produce a byte-identical
    file, breaking nest's core guarantee.
  - content_hash hashes DECODED canonical bytes -- the token-id codec MUST round-trip byte-exact
    (reversible markup, byte_fallback for any OOV) or citations and the STABLE-across-encodings
    content_hash guarantee break. Add a roundtrip assertion in the codec tests mirroring
    zstd_roundtrip_preserves_bytes.
  - Reject the C++/ICU dependency stacks. SentencePiece (proto2) and OpenNMT (ICU) bring heavy
    deps that violate the small-core, sovereign, offline, no-external-runtime mandate.
    Reimplement the merge loop / Viterbi / double-array trie in pure safe Rust (no panic, typed
    thiserror), each module <=300 loc (333 hard cap), single-responsibility.
  - Format additivity: only use RESERVED encoding ids (next free is 4; raw/zstd/f16/int8 occupy
    0-3) and section ids 0x09+ (0x07/0x08 taken). Do NOT bump NEST_FORMAT_VERSION (still 1)
    unless an existing field changes meaning -- a tokenizer section/encoding is purely additive
    and stays v1.
  - Per-file vocab adds bytes; on small or non-repetitive corpora the tokenizer section can cost
    more than it saves. Gate the codec behind a preset/heuristic (only emit when corpus size and
    repetitiveness clear a threshold) so default builds never regress in size, and always keep
    raw/zstd as the fallback encoding.
  - Keep the tokenizer config inline in the manifest, not as a companion file, or the
    single-file/self-describing/offline guarantee breaks. The tokenizer descriptor must also be
    folded into content_hash inputs so it is deterministic and tamper-evident.
  - bm25 requires alphabetical term order for determinism; subword segmentation changes the term
    set, so verify the sort still yields a stable, reproducible posting layout (the codec.rs
    already sorts terms by string -- subword terms must remain valid UTF-8 strings to keep that
    path).
  - Tokenizer perf is build-time, not serve-time, so do NOT add SIMD to the tokenizer (trie
    traversal is branch-bound, no dot-product) -- it would waste effort and the cited ARM port
    only used CRC32 for model-load hashing, not Viterbi. Keep the serve hot path purely mmap +
    SIMD cosine.
  - The ~150-200 loc merge loop and the Viterbi+trie decoder must split across files to respect
    the <=300 line rule (e.g. trie.rs, decode.rs, codec.rs) rather than one monolith; mirror the
    existing bm25/{index,codec,tokenize,fusion} single-responsibility split.
