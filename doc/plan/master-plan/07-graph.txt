==============================================================================================
nest pillar :: graph: first-class in-.nest knowledge graph + visual-first lens
layer: cross
==============================================================================================

a design doc. the executable steps are in ../tasks/.

thesis
----------------------------------------------------------------------------------------------
make the knowledge graph a first-class nest pillar, not a phase-4 csr afterthought. the graph
is THREE additive optional sections in the frozen .nest (a real property graph: entities,
typed edges, csr adjacency + columnar property tables), all reusing the intpack codec and
built/served exactly like hnsw and bm25: a candidate generator that always hands its frontier
to the SAME mandatory exact-cosine rerank (score_subset) so the returned score is real cosine
and graph traversal can never lie. the graph lives in two of the three redesign layers. in
NEST (the sovereign rust core) it is a flat, mmap-traversable csr walked with zero allocation
off disk, gated by typed thiserror, additive within frozen v1, never touching the embedding
hot path. in LENS (consumption) it is a SEPARATE visual-first viewer (cosmos.gl/webgl) that
reads the .nest through one stable, read-only graph-export api in nest-runtime and renders it;
the viewer is never compiled into the rust core, opens no socket beyond loading a local file,
and treats the audience that thinks in images and graphs (gifted, autistic, adhd) as a real
design driver: deterministic seeded layout, color/shape by entity type, focus+context
navigation, full keyboard control, progressive disclosure, low cognitive load. the discipline
that keeps this from bloating the core: the graph sections are OPTIONAL (excluded from
content_hash, so they never invalidate a nest:// citation), the heavy and possibly
non-deterministic entity/edge extraction lives in FORGE (python, outside the core,
profile-driven), and the engine ships incrementally - first the chunk-to-chunk csr that lets
nest drop chunk_overlap text, then the entity/typed-edge property graph, then the lens viewer.
catalog mode reuses the exact same graph sections: when blobs are referenced by content-hash
rather than inlined, the graph + index + text still live in the .nest and stay traversable, so
a giant osint monolith becomes a mmap-and-walk graph with no query-engine spin-up.

format impact
----------------------------------------------------------------------------------------------
all additive within frozen v1, zero NEST_FORMAT_VERSION bump. (a) one already-reserved + three
new named-constant OPTIONAL section ids: SECTION_GRAPH_ADJACENCY=0x0C (reserved today),
SECTION_GRAPH_NODES=0x11, SECTION_GRAPH_EDGE_PROPS=0x12, SECTION_GRAPH_ENTITY_MAP=0x13. all
excluded from content_hash (the canonical-six set at layout/mod.rs:114-121 is unchanged), so
adding a graph to a corpus never invalidates an existing nest:// citation. they join
OPTIONAL_SECTIONS only when their feature + manifest capability ship; until then section_name
does not resolve them and decode_payload fails closed, exactly like the existing reserved
0x09-0x10 block. (b) no new wire encoding ids needed: the graph reuses
SECTION_ENCODING_INTPACK=4 (delta+zigzag+bitpack csr offsets, neighbor-id gaps, edge-type
runs), float16=2 / int8=3 for inline edge weights, raw=0 for iso single-scalar edges. (c) new
per-section payload-version constants internal to each new section
(GRAPH_ADJACENCY_PAYLOAD_VERSION=1 etc.), bumped on internal layout change, never
NEST_FORMAT_VERSION - the same lane c discipline as HNSW_PAYLOAD_VERSION. (d) two additive
manifest capability flags (graph_present, graph_entities_present) in the existing manifest
capabilities map, no schema change. (e) the lens export json is a runtime artifact, not a
format section - it has its own GRAPH_EXPORT_SCHEMA_VERSION so the viewer and core evolve
independently.

architecture changes
----------------------------------------------------------------------------------------------
nest-format (frozen container, additive only): reserve four named-constant optional section
ids beyond the current 0x10 ceiling, same reservation pattern already used at
layout/mod.rs:102-109 - SECTION_GRAPH_ADJACENCY=0x0C is already reserved (csr edges); add
SECTION_GRAPH_NODES=0x11 (entity table: id + type-id + name-span + degree),
SECTION_GRAPH_EDGE_PROPS=0x12 (columnar typed-edge properties co-located with the csr:
edge_type u8, weight f16/int8, optional time/source-chunk columns),
SECTION_GRAPH_ENTITY_MAP=0x13 (entity-ordinal -> chunk-ordinal mention csr, the bridge from
entities back to citable spans). all four are optional, excluded from content_hash,
fail-closed on unknown id for old readers, emitted only when a manifest capability advertises
them. all integer payloads use SECTION_ENCODING_INTPACK=4; unweighted/iso edges store one
scalar (falkordb iso). new section codec modules under crates/nest-format/src/sections/graph/
(mod.rs + adjacency.rs + nodes.rs + edge_props.rs + entity_map.rs, each <=300 loc, repr(c) le,
thiserror). nest-runtime (mmap + serve): new module crates/nest-runtime/src/graph/ (mod.rs +
csr.rs reader + traverse.rs bounded-bfs + entity.rs + export.rs), mirroring
crates/nest-runtime/src/ann/. CsrIndex::from_bytes parses offsets+packed neighbors like
ann/codec.rs from_bytes; one node's neighbors are a single contiguous unpacked slice.
search_graph(query, k, hops, ef) seeds from exact-cosine top-k, bounded-bfs expands the
frontier over edges, unions with the seed set, and feeds the union to the EXISTING
score_subset rerank - identical contract to search_ann; recall stays f32::NAN (we never lie).
a read-only export api (graph::export::subgraph_json / neighborhood_json) returns a stable,
versioned json the lens reads. nest-cli: a 9th subcommand search-graph (mirrors search_ann.rs)
plus a graph-export subcommand that dumps a neighborhood or full subgraph as the lens-facing
json. nest-python (forge-facing): a build-time entity/edge writer in build_fn.rs that takes
forge-extracted entities + typed edges, canonically sorts them (ascending ids, alphabetical
types) for byte-identical output, and serializes the four sections. LENS is a brand-new
top-level directory lens/ (NOT a workspace crate, NOT in the rust core): a static
webgl/cosmos.gl viewer (typescript) that loads a .nest-exported graph json via the cli
graph-export or a tiny wasm reader, plus an accessibility-first interaction layer. ships as
its own thing, versioned against the export-json schema, never linked into
nest-format/runtime/cli.

ux
----------------------------------------------------------------------------------------------
cli verbs (additive, lowercase, mirror existing search-ann): `nest search-graph <file>
<query-json> -k K --hops H --ef N` (semantic seed -> bounded-bfs -> exact rerank; falls back
to exact search if no graph section, exactly like search-ann falls back when no hnsw), and
`nest graph-export <file> [--center <chunk_id|entity_id>] [--radius R] [--format cosmos|json]`
(dumps a neighborhood or full subgraph as lens-facing json, deterministic order). progressive
disclosure: with no graph section a .nest behaves identically to today; the graph is opt-in
capability, never a gate. the LENS viewer is visual-first and built for the
gifted/autistic/adhd audience as a primary design driver, not decoration: (1) deterministic
seeded force layout so the same .nest always renders the same map - pattern recognition
depends on spatial stability; (2) color + shape encode entity type, edge thickness encodes
weight, so meaning is visible pre-reading (low text load); (3) focus+context: click a node to
spotlight its k-hop neighborhood and dim the rest, with breadcrumb back-navigation, so you
never lose your place; (4) full keyboard navigation (arrow-walk edges, / to search, esc to
zoom out) and screen-reader labels on every node, so it is not mouse-only; (5) every node
links straight to its nest:// citation and exact span, so visual exploration and cited
retrieval are one motion; (6) a reduce-motion + high-contrast + dyslexia-friendly-font toggle
set, defaults conservative. accessibility is a feature of the flagship, not an afterthought.
the viewer is sovereign: it reads a local exported json or the local .nest, opens no network
socket, ships as static files.

phase placement
----------------------------------------------------------------------------------------------
graph is promoted from a single low-priority phase-4 card to a first-class pillar sequenced
across the consolidated phases, while respecting that intpack (phase 1) is its hard
dependency. tasks G1 (chunk-to-chunk csr adjacency + search-graph + drop chunk_overlap) lands
in PHASE 1 immediately after task #11 (HNSW/BM25 intpack re-encode), because it reuses the
exact same intpack primitive and pays for itself by deleting chunk-overlap text - this is the
old later/20 card, pulled forward and split. tasks G2 (entity/typed-edge property graph: nodes
+ edge_props + entity_map sections) and G3 (entity-aware graphrag traversal + export api) land
in PHASE 4 alongside the structured-tape work, since they depend on forge entity extraction
maturing. task G4 (lens viewer) is parallel and independent of the codec roadmap - it only
needs the export api (G3) and can be built by a web-focused agent without touching the rust
core, so it runs as its own track. priority: G1 HIGH (free text savings + delivers the named
graph-search gap), G2/G3 MEDIUM (the client-obsession knowledge graph), G4 MEDIUM but
high-visibility (the flagship demo surface for the pattern-lover vertical).

proposed tasks
----------------------------------------------------------------------------------------------
* G1 :: SECTION_GRAPH_ADJACENCY=0x0C chunk-to-chunk csr + search-graph subcommand + drop
  chunk_overlap
    goal:   deliver the named graph-search pillar at near-zero bytes: a flat csr chunk-to-chunk edge
            section (semantic-neighbor + NEXT_CHUNK + citation edges) reusing the intpack
            codec, traversed off mmap with bounded-bfs seeded from exact-cosine top-k and
            feeding the SAME mandatory exact rerank, plus a 9th cli subcommand. then reclaim
            text bytes by reconstructing neighbor context from NEXT_CHUNK edges so
            chunks_canonical can drop chunk_overlap. this is the old later/20 card pulled into
            phase 1.
    owns:   crates/nest-format/src/sections/graph/mod.rs,
            crates/nest-format/src/sections/graph/adjacency.rs,
            crates/nest-runtime/src/graph/mod.rs, crates/nest-runtime/src/graph/csr.rs,
            crates/nest-runtime/src/graph/traverse.rs, crates/nest-cli/src/cmd/search_graph.rs
      - define GRAPH_ADJACENCY_PAYLOAD_VERSION=1 and the csr layout in
        sections/graph/adjacency.rs: u32 version, u64 n_nodes, intpack-coded u64 offsets array
        (len n_nodes+1), intpack-coded delta-gapped neighbor-id blob, u8
        edge-type-per-neighbor run (iso single scalar when all edges one type, falkordb iso).
        all le, repr(c), thiserror on truncation, never panic. <=300 loc; split pack vs unpack
        if it grows.
      - wire SECTION_GRAPH_ADJACENCY (0x0C, already a named const in layout/mod.rs:105) into
        OPTIONAL_SECTIONS + section_name only behind a manifest capability graph_present,
        mirroring how hnsw/bm25 are gated; keep it excluded from content_hash (do not touch
        CANONICAL_SECTIONS).
      - build crates/nest-runtime/src/graph/csr.rs: CsrIndex::from_bytes mirroring
        ann/codec.rs from_bytes (ByteCursor pattern, typed errors), exposing neighbors(node)
        -> contiguous unpacked slice with zero allocation off the intpack blob; open it in
        mmap_file.rs::open behind the capability, like ann_index/bm25_index.
      - build graph/traverse.rs: bounded_bfs(seed_nodes, hops, max_frontier) over CsrIndex
        returning a deduped candidate Vec<usize> of chunk ordinals; pure integer, no scoring,
        generational visited buffer not a per-query HashSet.
      - add MmapNestFile::search_graph(query, k, hops, ef) in search.rs (or a thin graph
        submodule it calls): validate_query -> exact-cosine top-ef seed -> bounded_bfs expand
        -> union seed+frontier -> self.score_subset(union) -> sort_desc -> top-k.
        index_type="graph", recall=f32::NAN. fall back to self.search() when self.graph_index
        is None, exactly like search_ann.
      - add the 9th cli subcommand search-graph in main.rs Commands enum + cmd/search_graph.rs
        run(), mirroring search_ann.rs (file, query-json, -k, --hops, --ef); print_result via
        the existing util.
      - add the forge/build path: python build emits NEXT_CHUNK edges (sequential chunk
        ordinals) + top-m semantic-neighbor edges (from the already-built hnsw level-0 or
        exact knn) into the section, canonically sorted (ascending src, then edge-type, then
        dst) for byte-identical output; gate behind a build option, default off.
      - reclaim text: when NEXT_CHUNK edges exist, teach the builder to drop chunk_overlap
        from chunks_canonical and reconstruct neighbor context on read in materialize/search
        by concatenating adjacent spans; measure the chunks_canonical byte delta.
      - add a roundtrip+content_hash-equality test (mirror zstd_roundtrip_preserves_bytes):
        decode(encode(edges))==edges, and a fixed corpus with vs without the graph section has
        IDENTICAL content_hash. add a determinism test: two builds of the same edges =>
        byte-identical section. add a contract test: search_graph top-k scores byte-equal to
        search() rerank on the same union (graph only generates candidates, never changes
        scores).
    risk:   the graph frontier must ONLY generate candidates and the final score must be the exact-cosine
            rerank from score_subset, or the search contract is broken; assert search_graph
            scores equal exact rerank on the union, and never let a graph edge weight leak
            into the returned score. second risk: dropping chunk_overlap silently degrades
            recall if neighbor reconstruction is wrong - gate it on a recall@10-vs-baseline
            check and keep it opt-in.

  graph_entity_map 0x13)
    goal:   promote the chunk graph to a real knowledge graph: a node table of entities (id, type,
            name-span, degree), a columnar typed-edge property table co-located with the csr
            (edge_type, weight, optional time/source-chunk), and an entity->chunk mention map
            that bridges entities back to citable spans. all additive optional sections
            reusing intpack + terminusdb-style rank/select for property presence + falkordb
            iso for uniform columns. heavy entity extraction stays in forge (python), never in
            the core.
    owns:   crates/nest-format/src/sections/graph/nodes.rs,
            crates/nest-format/src/sections/graph/edge_props.rs,
            crates/nest-format/src/sections/graph/entity_map.rs,
            crates/nest-runtime/src/graph/entity.rs
      - reserve SECTION_GRAPH_NODES=0x11, SECTION_GRAPH_EDGE_PROPS=0x12,
        SECTION_GRAPH_ENTITY_MAP=0x13 as named consts in layout/mod.rs (extend the
        reserved-optional block past 0x10; add them to the reserved-ids test that asserts
        contiguity and content_hash exclusion). all excluded from content_hash, all
        fail-closed for old readers.
      - sections/graph/nodes.rs: entity table = intpack-coded parallel columns (entity_id
        ascending, type_id u8 dictionary-coded, name byte-span into a deduped name pool
        front-coded like chunk_ids, degree). order-preserving sorted layout so it is
        binary-searchable off mmap (blazegraph/terminusdb front-coding). <=300 loc.

        neighbor blob order from G1 - edge_type u8 (iso scalar if uniform), weight as f16/int8
        inline (nebula rank-as-sort-key co-location so traversal skips a separate lookup),
        optional time/source-chunk columns each with a terminusdb BitIndex presence bitmap so
        absent columns cost ~1 bit. iso single-scalar when a whole column is constant.
      - sections/graph/entity_map.rs: a second csr mapping entity-ordinal -> chunk-ordinal

        name), build the three sections byte-identically.
      - add per-codec roundtrip+content_hash-equality tests for all three sections, an
        iso-column test (constant column => one scalar), a presence-bitmap test (sparse
        optional column), and a determinism test (two builds byte-identical).
    risk:   this is where graph scope creep is most dangerous - it can drift into a general graph database

risks
----------------------------------------------------------------------------------------------
  - graph scope creep is the existential risk: a knowledge graph invites cypher, a query
    planner, a write path, and a mutable store - all of which violate keep-the-core-small +
    frozen-read-only-mmap. mitigation: the core ships ONLY flat readable csr + property
    columns + bounded-bfs + integer edge-type filter; no query language, no planner, no write
    path; anything richer lives in forge (build) or lens (view).
  - the candidate-generator contract is easy to violate: a graph edge weight or graphrag
    relevance could leak into the returned score, making it not real cosine. mitigation:
    search_graph must always end in score_subset (the mandatory exact rerank) and a contract
    test asserts graph scores equal exact rerank on the union; recall stays f32::NAN.
  - determinism: entity/edge extraction in forge is allowed to be non-deterministic, but the
    serialized sections must be byte-identical for a fixed entity set or reproducible builds
    break. mitigation: the canonical sort in the writer (ascending ids, alphabetical types) is
    the determinism anchor, asserted by a two-build byte-identical test per section.
  - section-id exhaustion + content_hash safety: cramming entities+edges+props into one
    section breaks the 300-line single-responsibility rule, but adding ids past 0x10 must stay
    additive and content_hash-excluded. mitigation: reserve 0x11/0x12/0x13 as named consts in
    the same reserved-optional pattern, extend the existing contiguity+exclusion test, never
    touch CANONICAL_SECTIONS.
  - dropping chunk_overlap to save text bytes can silently degrade recall if neighbor
    reconstruction is wrong. mitigation: keep it opt-in, gate on a recall@10-vs-baseline
    check, and reconstruct only from NEXT_CHUNK edges that are present.
  - the lens export json is a public contract; an unversioned schema silently breaks the
    viewer on every core change. mitigation: GRAPH_EXPORT_SCHEMA_VERSION + a snapshot test,
    and the viewer refuses mismatched versions.
  - the lens viewer could accidentally pull the project online (cdn cosmos.gl, remote fonts)
    breaking offline-by-construction. mitigation: lens/ stays out of the cargo workspace,
    vendors its deps locally, and a check asserts no remote fetch().

open questions
----------------------------------------------------------------------------------------------
  - should the chunk-to-chunk csr (G1) and the hnsw level-0 adjacency be unified into one
    section to avoid storing two graphs, or kept separate because hnsw is symmetric-undirected
    while NEXT_CHUNK/citation edges are typed and directed? leaning separate for clarity, but
    a shared csr with an edge-type byte could save bytes.
  - for catalog mode (blobs referenced by content-hash, not inlined), do entity mention spans
    point into the referenced blob via the sidecar content-hash map, or only into the inlined
    canonical text? needs the catalog-mode pillar's blob-reference design to land first.
  - should edge weights ride the same quantization ladder as embeddings (f16/int8/int4) or
    stay f16-only? edges are a tiny fraction of bytes, so int8 is likely premature
    optimization - confirm with a measured edge-section size on a real osint/etymology corpus.
  - where exactly does the score_subset rerank for graph candidates need the embeddings_fp
    rerank source (phase 0, task #06) when the preset is sub-int8? the graph frontier feeds
    the same rerank, so it inherits the same honesty gate - confirm G1 depends on #06 only
    when shipped on a sub-int8 preset.
  - does the lens viewer read the .nest directly via a wasm build of nest-runtime's export api
    (one source of truth, heavier build) or only consume the cli graph-export json (simpler,
    looser coupling)? leaning cli-json for v1 to keep lens fully decoupled from the rust core.
  - for the pattern-lover vertical (voynich/gematria/unicode/etymology), are symbol/glyph
    similarity edges first-class typed edges in the graph, or do they belong to the multimodal
    embedding-space pillar with the graph only linking entities? this is the seam between the
    GRAPH pillar and the MULTIMODAL pillar and needs one owner.
